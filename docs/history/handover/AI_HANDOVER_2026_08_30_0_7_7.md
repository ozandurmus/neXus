## 2. Recent builds (this session) — landed on this session's branch

Detail is in `project/build_history.json`; phase doc under
`docs/history/phase/`.

- **`compliance_trend_reconstruction` (0.7.7)** — offline retro-fill for
  `compliance_overview.history[]`. Follow-up to `0.7.5`'s deliberate
  no-backfill decision. **Feasibility finding put to the product owner
  before writing any code:** most of `build_compliance_posture`'s inputs
  (alignment, CP structured config, control-assignment/waiver policy, CE.1
  user checks) are not versioned per historical CAS snapshot, so a faithful
  full re-run is impossible. Owner chose narrow/labeled reconstruction over
  dropping the build or a broader silent approximation. Delivered exactly
  that: `utils/compliance_trend_reconstruction.py`
  (`reconstruct_pan_baseline_records`) mines stored PAN effective-running
  CAS snapshots, single-linkage time-clusters them into synthetic checkpoints
  (CAS has no `run_id` to group by), and evaluates the ten deterministic
  `DEFAULT_RULE_PACK` baseline controls per entity through the exact same
  live evaluator dispatch (`compliance_posture._evaluate_vendor_neutral_control`)
  a real checkpoint uses — PAN only, no alignment, no CP, no
  assignment/waiver replay, no CE.1. Every record carries `reconstructed:
  true` / `reconstruction_scope: "pan_baseline_rule_pack_only"`.
  `utils/compliance_history.py` gained `append_reconstructed` (idempotent on
  `run_id`) and `history_view`'s trend delta now always compares against the
  newest **live** record, never a reconstructed one — even when a
  reconstructed record is chronologically newest in the ledger. New offline
  `main.py --compliance-trend-reconstruct` maintenance mode (no network, no
  credentials, mutually exclusive with the other maintenance/collection/render
  modes). `static/app.js`'s `complianceSparkline` renders reconstructed runs
  of the polyline dashed/hollow/reduced-opacity; a live and a reconstructed
  point never share one continuous solid segment. Full record + evidence:
  `docs/history/phase/0_7_7_COMPLIANCE_TREND_RECONSTRUCTION.md`.

## 4. Open risks / debt carried forward

- CP device-interaction-safety audit remains P0 — hard prerequisite for CE.2.
- `0.7.7` reconstruction bucketing is a time-gap heuristic (default 15
  minutes), not a real run correlation — CAS metadata carries no `run_id`.
  If a real fleet's PAN-config collection stage ever runs long enough to
  exceed the gap on its own, entities from one real checkpoint could split
  across two reconstructed buckets. Not observed against real data yet
  (no server); reconfirm the default once real CAS history exists.
- `0.7.7`'s `catalog_version` on a reconstructed record is always *today's*
  catalog (rules aren't versioned historically either) — a reconstructed
  point older than the catalog's own history should be read as "what today's
  rule pack would have found," not "what was reported at the time."
  Documented in the phase doc; worth a UI tooltip on the dashed segment if a
  future build touches this surface again.
- `unified.interfaces` / `unified.routes` join is an exact normalised-identity
  match on the config-UI device name. Confirm the join lands on the first
  real-env run before authoring interface/route packs.
- `0.7.5` trend ledger: aggregates only, no backfill for *live* records — a
  catalog / control-set version change between runs is recorded per-record
  but not annotated on the trend line.
- The `uitest` fixture is authored at the payload layer — if a builder
  changes its output shape, the fixture must be regenerated to match.
- The regex safety linter (`_REDOS_RE` + quantifier count + `.*.*`) is
  best-effort; the eval-time timeout is the real backstop.
- `0.7.4` framework catalog requirement lists are hand-authored.
- The CAS / support-key path writes `data/` + `logs/` into the repo dir
  during a test run (`DEV.0.3C` deferred). Gitignored; delete before the
  privacy gate.
- `scripts/pytest_one_shot.ps1` calls `py` → 3.14 without deps
  (`dev_python_env_tooling_friction`).
- The bun+happy-dom render-harness path can break on a `window.eval` gap
  depending on the installed bun version; the Playwright fallback
  (`tools/render-harness/check_render_playwright.py`) exists for exactly this
  and is what this session used.
