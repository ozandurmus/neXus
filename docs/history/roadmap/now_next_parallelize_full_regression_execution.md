# PARALLELIZE_FULL_REGRESSION_EXECUTION — parallelize_full_regression_execution: DEV.TEST.1 -- Parallelize local and GitHub Actions full-regression execution

- Root cause audit: the workflow's own long-standing 'serial on purpose' comment traced to a single concrete defect -- scripts/render_uitest.py::render() left three utils.html_export payload builders bare-rebound (not monkeypatch.setattr) after use, so the rebind silently outlived the call and leaked into whichever later in-process run_html_export() shared its worker/process, two order-dependent failures under -n auto historically hid about two runs in three. That defect is already fixed with a try/finally restore (scripts/render_uitest.py::_injected_builders) and directly regression-tested regardless of worker or ordering (tests/test_frontend_rendering_boundary.py::test_render_uitest_restores_the_builders_it_injects) -- confirmed by reading both files; no other shared-mutable-resource pattern (fixed ports beyond OS-assigned port 0, os.chdir, module-global caches, tracked-file mutation) was found across tests/. Candidate A (one pytest-xdist process, `-n auto --dist worksteal`) selected over a fixed worker count or matrix sharding: it is the exact command already proven locally and in scripts/pytest_one_shot.ps1/requirements-dev.txt/docs/AI_DEVELOPMENT_PROTOCOL.md, needs no shard-membership/aggregation machinery, and a single xdist master process already yields one aggregate exit code across every worker so no worker's failure can be masked.
- Changed: .github/workflows/validation.yml full-regression job's 'Full test suite' step (serial -> `python -m pytest -q -n auto --dist worksteal`, plus a worker-topology visibility step); tests/test_ci_workflow_fast_pr_regression.py's FULL_SUITE_LINE constant/assertions to match; docs/AI_DEVELOPMENT_PROTOCOL.md 'Test execution economy'/'CI validation policy', AI_START_HERE.md validation ladder, CLAUDE.md 'Test economy' -- all now recommend the parallel command as the default full-suite path, with `-n0`/`-Serial` documented as an explicit diagnostic override only, never the default. Preserved: the `validate` job unchanged, every non-full-suite gate (privacy, project-state consistency, build-history index, whitespace check), scripts/pytest_one_shot.ps1 (already parallel-by-default, unmodified), and every targeted/subsystem test invocation (still serial where already serial -- e.g. tests/test_architecture_convergence.py alone in both gates).
- Local validation: `python3 -m pytest -q -n auto --dist worksteal` (4 CPUs, auto-detected) -- 1957 passed, 24 skipped, 0 failed in 35.01s wall-clock (this sandbox; one test's skip/pass split vs. the 1958/23 prior baseline is an environment-dependent Playwright/Chromium resolution difference, not a coverage change -- 1981 collected either way). No serial full-suite run performed as evidence per this movement's own validation ladder (a local serial run would misrepresent cloud timing and is not required once the specific known leak is fixed+guarded).
- PR-trigger expansion attempted, then reverted (Product Owner direction, same session): a follow-up commit removed full-regression's `if: github.event_name != 'pull_request'` guard so it would also run on every pull_request, to get automatic pre-merge cloud proof. - CORRECTION -- post-merge YAML-syntax incident (2026-09-06), an in-session misdiagnosis corrected: while chasing cloud proof, every check suite for every trigger (push, pull_request, workflow_dispatch) on every branch -- including, after merge, the merge commit on main itself -- completed with zero jobs. This was FIRST MISDIAGNOSED as an environment/automation-identity limitation (`workflow_dispatch` returning `403 Resource not accessible by integration` on non-default branches, and check suites for this session's automation identity completing with zero jobs on both push and pull_request events) preventing GitHub Actions from scheduling jobs on a non-default branch. That diagnosis was WRONG. Parsing the workflow file locally after merge found the real cause: the 'Report worker topology' step's `run:` value was an unquoted plain YAML scalar containing a bare `: ` inside an f-string label ("...target): {os.cpu_count()}"), which YAML parses as an illegal nested mapping -- a file that fails to parse cannot schedule a job under any trigger, on any branch, regardless of who pushed it, which is exactly the symptom observed. Fixed by rewording the f-string in a narrow post-merge follow-up. A new regression guard, tests/test_ci_workflow_fast_pr_regression.py::test_workflow_yaml_parses (pyyaml>=6 added to requirements-dev.txt), now actually parses the workflow file on every test run so this exact defect class fails locally before push, not silently after merge. The PR-trigger policy decision in the prior note was not reopened by this correction -- it was made independently and stands on its own merits.
- Pre-merge evidence decision (Product Owner, this session): two clean complete local parallel runs were accepted as this movement's pre-merge full-suite evidence in place of a PR-triggered cloud run -- 1981 collected, 1957 passed, 24 skipped, 0 failed, at 32.27s and 35.01s (4 workers, `-n auto --dist worksteal`).
