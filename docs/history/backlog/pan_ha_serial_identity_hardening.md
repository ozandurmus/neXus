# PAN HA pair operational identity should consider serial, not just hostname

status: planned · target: Pre-CLASS-2 (OP.0b/OP.2) architecture decision

OP.0a.P7's PAN HA peer-pairing identity closure (docs/history/phase/OP_0A_PAN_HA_PEER_PAIRING_IDENTITY_CLOSURE.md) found that PAN entity identity (utils.restore_readiness.resolve_entity_id) is hostname-based; hostname is mutable (admin rename), unlike serial, which is already collected on every PAN row in both parsers and already used elsewhere in configuration/panorama_config_collector.py (_collect_direct_compare's identity_mismatch check) as this codebase's own precedent for authoritative device identity. The pairing closure deliberately did not migrate entity_id to serial -- too large a change for a narrow fix, touching every PAN entity_id consumer and existing tests. A deliberate identity-hardening decision belongs before OP.2's identity gate (FAILOVER_ENGINE_ARCHITECTURE.md section 10.1) can depend on PAN pair identity being stable under any real-world hostname change. UPDATE 2026-09-09 (PAN_HA_SERIAL_IDENTITY_HARDENING_DECISION_DOCUMENT, relay NXS-LOCAL-0039): decision document at docs/design/PAN_HA_SERIAL_IDENTITY_HARDENING_DECISION.md. Nine real non-test consumers of resolve_entity_id found by grep (utils/restore_readiness.py, utils/recovery_validation.py, utils/recovery_collect.py, utils/failover/assessment.py x4 call sites, application/workflows/preflight.py, console/app.py), plus three persisted-record consumers of its output value (utils/recovery_store.py's on-disk vault path, utils/config_storage.py/config_history.py's snapshot lookup key, utils/operate/store.py's lock/quarantine key). Key finding: FAILOVER_ENGINE_ARCHITECTURE.md section 10.1 item 2 ('PAN requires the serial identity gate') names a fresh execution-time verification, not a resolve_entity_id namespace migration -- that gate already exists in nascent form (panorama/preflight_collector.py's P1 identity gate, exact-string serial comparison, distinct from the hostname-based physical_device_identity label) -- so the backlog note's framing conflates two separable questions (Q-A: should the collector-identity namespace migrate to serial; Q-B: does OP.2's gate requirement already need that). A hostname-rename-in-place DOES need a data migration for already-persisted records, independent of which option is chosen -- sketched (design only) in the document section 6: recovery vault directories and config-history keys fork at the rename boundary today with zero reconciliation mechanism for PAN (the M8 device_identity_relationships supersession mechanism exists but is CP-only, VENDOR_NAMESPACES=('checkpoint',)). NOT FREEZABLE NOW: three independent PO-level reasons -- (1) the Q-A/Q-B scope-fit question itself, (2) the open P0 pan_serial_representation_identity_evidence_closure item (AWAITING_PO, real-environment MATCH/MISMATCH anomaly on the same serial-identity comparison, root cause unknown) directly undercuts trusting serial as a foundation right now, (3) the persisted-record migration is substantial cross-cutting engineering work needing its own contract. Preliminary lean (not a freeze-ready recommendation): narrow any near-term fix to hardening the existing execution-time serial gate (Option C in the document) rather than migrating resolve_entity_id, but this does not resolve reasons 1 or 2. Disposition: RELAY_NOTE / AWAITING_PO appended to relay/NXS-LOCAL-0039-*.json requesting a PO DECIDE episode before either Option A/B/C is adopted.
