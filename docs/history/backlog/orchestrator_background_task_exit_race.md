# An engineer's own claude -p background task can outlive its process's turn, leaving staged-but-uncommitted work when the session exits without waiting

status: automated_validated · target: scripts/orchestrator.py::_spawn_engineer and/or the ENGINEER_PROMPT -- observed live during relay/NXS-LOCAL-0018 (PR #133 merge-conflict completion), 2026-09-08

Real bug, observed live, not hypothetical. relay/NXS-LOCAL-0018's engineer session staged its merge-conflict-resolution changes (`git add`), then ran the full pytest regression via the claude CLI's own internal background-task mechanism (the run exceeded a 120s foreground timeout and was auto-moved to the background, e.g. `Command did not complete within its 120s timeout and was moved to the background (ID: bhpt1icqs)`). The session's own turn then ended (it printed a final assistant message and returned `result (success)`) WITHOUT waiting for that background task's completion notification -- the orchestrator's process record then showed `pid_alive: false` with the relay still at `SESSION_START` (no RELAY_ACK/NOTE/QUESTION/CLOSE ever posted) and the worktree left with everything staged but not committed (`git status --short` showed all changes in the index, nothing in `git log`). Recovered this time by a plain `orchestrator start` resume, which happened to pick the work back up cleanly (no data loss), but this is not guaranteed in general -- a background task producing a result the next resumed session never sees, or resuming mid-way through an unverified test run, is a real correctness gap for the standing 'green tests -> self-merge' authorization (relay#13): a session must not be able to reach a commit/push/merge step on the strength of a background test run it never actually waited to see the result of.

Fix direction (not yet designed in detail -- needs its own investigation before a SESSION_START is written): (a) the ENGINEER_PROMPT (scripts/orchestrator.py) could be strengthened to explicitly instruct every engineer session to never treat a long-running validation command as backgroundable -- always run the full regression suite as a foreground, awaited command, even past whatever timeout the CLI would otherwise auto-background it at (this may need a per-invocation flag/env var to raise or disable that auto-background threshold for engineer sessions specifically, if one exists -- verify before assuming); (b) alternatively/additionally, the orchestrator's own resume path (decide_start) could detect this specific pattern (index has staged-but-uncommitted changes, relay never advanced past SESSION_START, pid dead) and inject an explicit instruction into the resumed session's context to first check for and finish any prior staged-but-uncommitted work and any background task results before proceeding, rather than relying on the resumed session to figure this out unprompted (it did, this time, but that's not yet a guarantee). Report via RELAY_QUESTION if investigation finds the CLI gives no way to control or query this background-task behavior from outside the session.

Not urgent-blocking (recovery worked this time via a plain resume), but real and worth fixing before it causes an actual lost-work or premature-merge incident rather than just an extra resume cycle.

Priority raised P1 -> P0 on 2026-09-08 per explicit Product Owner direction: this is the one concrete engineering item among this session's PO-orchestration-efficiency findings (see PRODUCT_DIRECTION_RECORD.md section 14), and the standing relay#13 'green tests -> self-merge' authorization must not remain exposed to an unverified background test result. RESOLVED 2026-09-08 (relay/NXS-LOCAL-0019): confirmed pre-fix that ENGINEER_PROMPT did not instruct engineer sessions to run validation in the foreground regardless of the CLI's auto-background timeout, and that decide_start's resume path had no detection for the dead-pid-plus-staged-changes pattern. (a) ENGINEER_PROMPT strengthened: never treat a long-running validation command as backgroundable; run it foreground/awaited with an explicit long timeout; if the CLI backgrounds it anyway, wait for and read the real result before committing/pushing/merging. Investigated the installed claude CLI's own shipped behavior directly: it reads BASH_DEFAULT_TIMEOUT_MS (default 120000ms -- exactly the incident's '120s timeout') as the fallback timeout for a Bash-tool call without its own explicit timeout, and BASH_MAX_TIMEOUT_MS, floored at that default, as the ceiling on an explicit one -- a real lever exists, so scripts/orchestrator.py::_spawn_engineer now sets BASH_DEFAULT_TIMEOUT_MS to 1_800_000 (30 min) in the engineer's own env (setdefault, never overriding an operator's own value), raising both; this does not disable auto-backgrounding outright (no such switch found) -- the prompt instruction is what the guarantee actually rests on. (b) decide_start's resume branch now calls new pure functions (relay_never_advanced_past_session_start / has_staged_uncommitted_changes / needs_resume_recovery_note; git status parsed, never spawned inside the pure functions) and, when the pattern matches, injects RESUME_RECOVERY_NOTE onto that one resume's prompt via _spawn_engineer's new extra_prompt_note parameter -- dispatch/refuse/ordinary-resume decisions are unchanged. Targeted tests added to tests/test_orchestrator.py; full one-shot regression green modulo two pre-existing, unrelated failures (see build_history.json).
