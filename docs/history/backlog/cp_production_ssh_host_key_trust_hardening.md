# CP SSH host-key trust: mandatory strict enforcement for production/container runtime

status: planned · target: production container/pod runtime hardening (post-DEPLOY.1)

PO decision 2026-09-03 (OP_0B_1_COMMAND_GATE_PACKAGE.md "CP SSH trust -- PO override, development compatibility mode"): the OP.0b S5 CP HA preflight feature (checkpoint.preflight_collector.run_cp_preflight) defaults strict_host_key=False for the current development/pre-production phase, matching every other CP SSH caller's existing compatibility-mode default -- mandatory strict enforcement is deliberately deferred to the future production/container-pod runtime, not implemented now, to avoid investing in workstation-specific Paramiko trust-management machinery ahead of that migration. Strict mode itself remains fully implemented, fail-closed and selectable today via strict_host_key=True; utils.cp_ssh_trust.apply_strict_host_key_policy is unchanged. This item is the production checklist for closing that deferral. Scope: (1) mandatory strict host-key verification for the production runtime -- no compatibility-mode default once containerized; (2) container/pod known_hosts provisioning mechanism (bind-mount or equivalent, matching deploy/secrets/ conventions); (3) independently verified host-key enrollment/provisioning procedure -- no TOFU, no ssh-keyscan-as-trust, out-of-band fingerprint verification required; (4) host-key rotation procedure; (5) mismatch handling (BadHostKeyException stays a distinct, non-retryable, fail-closed rejection); (6) missing-host-key handling (HostKeyNotTrustedError stays a distinct, non-retryable, fail-closed rejection -- see host-key-retry-classification finding below); (7) no automatic promotion of an OBSERVED_UNVERIFIED compatibility-mode fingerprint to trusted status, ever; (8) production startup/preflight should positively prove trusted host-key material exists before the runtime is considered ready, not merely fail closed on first connection attempt; (9) migration away from workstation-specific trust assumptions (a developer's own ~/.ssh/known_hosts) toward a runtime-owned, deployment-provisioned trust store. Host-key-retry-classification finding folded in here rather than a separate item: op0b_s8_host_key_retry_classification (HostKeyNotTrustedError, merged 2026-09-03, PR #47) already made a missing-host-key rejection non-retryable in both CP SSH retry loops; this item tracks keeping that guarantee true as production hardening proceeds, not redoing it. Reconciled with, not duplicating, the narrower cp_ssh_trust_r2_prod_server item (DEPLOY.1 Ubuntu/Docker server R2 validation for the existing CP config-collection path) -- that item's obligation is one line item under this broader checklist. Do not claim strict production hardening is complete until this item closes; the current state is deliberately, explicitly INCOMPLETE by PO decision, not a regression.
