# Check Point VSX per-VS interface/route reads return the physical member's data, not the virtual system's own

status: planned · target: 

Measured live against CLS-BEACON-02: the physical context, VS-BEACON-02-55 (VSID 2), and VS-BEACON-02-20 (VSID 3) all return byte-identical interface names, addresses and member_addresses (Mgmt, Sync, lo -- same member IPs in all three). Only the physical context's cluster VIP differs (correctly not merged into the VS contexts after this session's fix). The per-VSID read (bash -lc 'vsenv <VSID> && ip -4 addr show && ip -4 route show') is not actually returning virtual-system-scoped data -- it returns the physical member's own interfaces regardless of VSID, the same class of vsenv-scoping problem already found and partially fixed for cphaprob this session (see cp_cluster_vip_never_observed_in_fleet). This mirrors the already-documented D-UI2 gap in UI2_INVENTORY_AND_CONFIGURATION_DESIGN_LANGUAGE.md, which records the identical limitation for the Configuration plane's interfaces/routing sections ('collected without a virtual system context ... what is held under those two sections is the member's view rather than each virtual system's'). Root cause is likely structural: Check Point VSX's generic Linux 'ip' command may not be network-namespace-isolated per virtual system the way vsenv changes the Clish/cphaprob context, so no vsenv-wrapped 'ip addr show' variant will produce genuinely per-VS output -- a different, VSX-aware command is needed (research required, per AGENTS.md vendor semantics law, before any fix is attempted). Do not guess another flag; this needs official Check Point VSX documentation research on the correct per-VS interface/route read before implementation.

Root cause found and fixed 2026-09-21: not a vendor limitation. buildCheckPointBatchCommand() sent the whole per-VSID batch as a bare SSH exec command (channel.setCommand(), no shell wrapper). vsenv is a shell function defined only in the Expert login-shell profile, so every 'vsenv <VSID> || true' in the unwrapped batch silently failed (command not found, swallowed by || true), the context switch never happened, and every VSID section re-read the same physical ip/route output. checkPointPhysicalCommand/checkPointVsidSteps already wrapped their reads in bash -lc for this exact reason; the batch optimization did not. Fix: wrap the whole batch body in one bash -lc '...' (echo markers switched to double quotes to avoid quoting collision). Needs HOST-A build/deploy + live re-check on a real VSX cluster before this item can move to done.

Follow-up 2026-09-21: the bash -lc batch fix alone was not sufficient. After a fresh collect (post-fix), FW-CKPINTRA-CLS's VS-1 and VS-2 contexts still showed a suspicious repeating /28 address sequence starting from the same base. Root cause: chaining multiple vsenv <vsid> context switches for DIFFERENT VSIDs inside one shared bash -lc process does not reliably re-scope every later read to its own VSID. The Product Owner's own manual reproduction issues one standalone bash -lc process per VSID and gets correct output every time. Real root cause found and fixed 2026-09-21 (PO live-tested and confirmed): fw getifs/ip addr show, run inside a vsenv <VSID> context, returns an internal VSX addressing scheme on a genuine ClusterXL cluster member -- NOT the real configured address ('sanal IP donuyor', PO's own words) -- while it is correct on a standalone (non-clustered) VSX gateway. cphaprob -a if, vsenv-scoped, is what actually reports a cluster member's real, distinct per-VS cluster-interface addresses; PO proved this live on <DEVICE_NAME> (VSID 2 and VSID 3 each returned correct, genuinely different real subnets via cphaprob -a if, while fw getifs on the same box/VSIDs returned the bogus uniform <PRIVATE_IP>/24 sequence).
