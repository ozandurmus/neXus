# Check Point VSX per-VS interface/route reads return the physical member's data, not the virtual system's own

status: planned · target: 

Measured live against CLS-BEACON-02: the physical context, VS-BEACON-02-55 (VSID 2), and VS-BEACON-02-20 (VSID 3) all return byte-identical interface names, addresses and member_addresses (Mgmt, Sync, lo -- same member IPs in all three). Only the physical context's cluster VIP differs (correctly not merged into the VS contexts after this session's fix). The per-VSID read (bash -lc 'vsenv <VSID> && ip -4 addr show && ip -4 route show') is not actually returning virtual-system-scoped data -- it returns the physical member's own interfaces regardless of VSID, the same class of vsenv-scoping problem already found and partially fixed for cphaprob this session (see cp_cluster_vip_never_observed_in_fleet). This mirrors the already-documented D-UI2 gap in UI2_INVENTORY_AND_CONFIGURATION_DESIGN_LANGUAGE.md, which records the identical limitation for the Configuration plane's interfaces/routing sections ('collected without a virtual system context ... what is held under those two sections is the member's view rather than each virtual system's'). Root cause is likely structural: Check Point VSX's generic Linux 'ip' command may not be network-namespace-isolated per virtual system the way vsenv changes the Clish/cphaprob context, so no vsenv-wrapped 'ip addr show' variant will produce genuinely per-VS output -- a different, VSX-aware command is needed (research required, per AGENTS.md vendor semantics law, before any fix is attempted). Do not guess another flag; this needs official Check Point VSX documentation research on the correct per-VS interface/route read before implementation.
