# Device display falls back to the management IP for every cluster member: the discovery lateral join excludes any candidate that has a parent, so name, model and cluster reference are all lost

status: planned · target: JooqDeviceRepository DEVICE_SELECT lateral join; regression from 9f46cc0 (NXS-LOCAL-0346)

Measured on the live deployment 2026-09-20. The lateral join onto discovery_candidate ends with 'and c.parent_candidate_id is null'. Every cluster member candidate carries a parent (its cluster): PLAIN_CLUSTER_MEMBER 34 of 34, PHYSICAL_VIRTUALIZATION_CHASSIS_MEMBER 14 of 14, and no other kind carries one. Running the join's own predicate over the device table gives devices=107, join_resolved=59, join_failed=48 -- exactly the 34+14 members. When the join fails, the select's coalesce chain falls through: coalesce(d.observed_hostname, dc.display_name, ep.address_ref). observed_hostname is 0 of 107 because enrollment confirm has not run, so the row renders the management address instead of a name, and model, software version and cluster_member_ref come from the same join and disappear with it. One predicate therefore explains three reported symptoms: half the list showing an address instead of a hostname, model reported as unknown for a device the product can reach, and cluster view appearing for only some clusters. The condition was introduced by 9f46cc0 to stop Palo Alto candidates matching a child row, so removing it outright would reopen that. Preferring a parentless candidate rather than excluding parented ones keeps both intentions: order by (c.parent_candidate_id is null) desc before limit 1.
