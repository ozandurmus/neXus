# Cluster membership is known at discovery but does not reach enrolled devices: 48 member candidates carry a cluster reference while only 6 device rows do, and no ENROLLED device has one

status: planned · target: enrollment/confirm path writing devices.cluster_member_ref

Measured on the live deployment 2026-09-20 after a fresh discovery run. Every member candidate carries its cluster: PLAIN_CLUSTER_MEMBER 34 of 34 and PHYSICAL_VIRTUALIZATION_CHASSIS_MEMBER 14 of 14 have cluster_reference set, so discovery parsed the membership correctly. The source only states it one way -- a cluster object lists cluster-member-names, while a member object carries no reference back to its cluster -- and the adapter already builds the name-to-cluster map from the cluster objects, which is why all 48 resolve. On the device side only 6 rows carry cluster_member_ref, across 3 clusters, and all 3 are DRAFT. The 60 rows in ENROLLED carry none at all. So membership is established at discovery and then lost on the way to, or at, enrollment confirm. Note the interaction with discovery_lateral_join_drops_cluster_members: the select reads cluster_member_ref through coalesce(c_parent.display_name, d.cluster_member_ref, dc.cluster_reference), and two of those three sources come through the same lateral join that currently excludes members, so the two defects mask each other and both must be measured again after either is fixed.
