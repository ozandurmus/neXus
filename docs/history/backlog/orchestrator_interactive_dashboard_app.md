PRODUCT OWNER'S EXPLICIT REQUIREMENTS (verbatim intent preserved): (1) a real clickable app, not a terminal redraw loop; (2) it reads the orchestrator's own state, and the refresh interval must be changeable from inside the UI itself (persisted, not only a --interval CLI flag); (3) a list of all tasks/movements; (4) clicking one opens a full detail view; (5) at a glance: what is currently being developed, what has already been developed (done/merged), and what stage each active movement is at, grouped active-on-top / recently-done-in-the-middle / closed-at-the-bottom, not one flat list.

PRIOR ART SURVEYED (what comparable local dev-tool dashboards do, and what to borrow): CI/job dashboards (GitHub Actions run list, Airflow DAG-run UI, Prefect/Dagster run UI) all share the same shape -- a grouped/filterable run list with a colored status badge, a click-through detail view with a tabbed layout (overview / logs / timeline), and a live-tailing log pane. Process managers (pm2, Docker Desktop/Portainer, k9s) add the 'what's alive right now' angle: liveness derived from the actual OS-level process/container check, never from a timestamp alone -- confirms this movement's own finding that pid_alive, not heartbeat_at, is the only honest liveness signal today. The consistent architectural pattern across all of them for a single-user local tool: a thin local backend that already owns the ground truth (here: scripts/orchestrator.py's state dir + relay/*.json + each worktree's git status) exposes a small read JSON API; a static single-page frontend polls or subscribes to it; no user accounts, no multi-tenancy, bind to localhost only.

RECOMMENDED ARCHITECTURE (REQUIRED unless the engineer session finds a concrete blocker, reported via RELAY_QUESTION): (A) Backend -- a new `python3 scripts/orchestrator.py dashboard [--port N, default e.g. 8765] [--relay-dir] [--state-dir]` subcommand, stdlib-only (http.server/socketserver/wsgiref -- matches the existing 'no new third-party dependency' invariant already enforced for orchestrator.py and local_relay.py), bound to 127.0.0.1 only. It serves (a1) one static HTML/CSS/JS page (vanilla, no build step, single file or a small handful under a new scripts/dashboard_assets/ or similar -- no npm/webpack/node toolchain in this repo, do not introduce one), and (a2) a small JSON API reusing the existing status-computation functions (_status_row, _read_last_activity, _heartbeat_age_seconds etc.) rather than re-implementing them: GET /api/movements (grouped list), GET /api/movements/<id> (detail: full .nexus/approved_task.json acceptance criteria, complete relay entry history in order with actor+marker+timestamp+body, git worktree status --porcelain parsed into a human label, ahead/behind origin/main counts, open PR number+state+CI conclusion via `gh pr list --head <branch>` if `gh` is available -- degrade gracefully to 'n/a' if not, never crash), GET /api/movements/<id>/log (tail of engineer.summary.log, or engineer.log if the summary doesn't exist yet, capped at a reasonable byte count), GET/PUT /api/config (currently just {"poll_interval_seconds": N}, persisted to a small JSON file e.g. .nexus/dashboard_config.json at the repo root -- not per-worktree). (B) Frontend refresh: plain polling via fetch() at the UI-configurable interval is sufficient and simplest (avoid SSE/WebSocket complexity unless the engineer session judges it trivial with stdlib alone -- do not add a dependency for this). (C) Real per-movement 'stage' string (addresses a gap this Product Owner already found in the existing terminal watch): derive from git worktree status instead of trusting heartbeat_at alone -- e.g. 'not started yet' (only SESSION_START posted, no worktree changes), 'developing' (uncommitted changes present), 'resolving merge conflict' (UU/AA porcelain markers), 'ready to push' (committed, no PR yet), 'PR open, CI running/red/green' (via gh), 'merged' (relay CLOSED + PR merged). (D) heartbeat_at itself: either make it genuinely periodic (the spawned engineer process or a lightweight orchestrator-side poller updates it on a real signal) or rename/relabel it honestly in both the API and the UI so it is never presented as liveness -- pid_alive stays the authoritative liveness check either way. (E) Grouping in the UI: active (phase running, pid_alive true) on top; done-but-recent (phase done, e.g. within the last N hours or last N items) in the middle; closed/merged in a collapsed-by-default bottom section -- exactly the three-tier grouping the Product Owner asked for. (F) Detail view tabs/sections: Overview (objective, acceptance criteria, current stage, branch, worktree path, PR link), Relay history (the full ordered marker log -- this is the audit trail GOV.PO.3 already relies on, so surfacing it in the UI is pure value, no new data), Log (live-tailing engineer.summary.log with fallback to raw engineer.log). (G) Read-only by default, mirroring 'orchestrator watch' and 'local_relay.py watch' precedent -- no start/stop/resume/merge action buttons in this first version; that would be a new write surface crossing back into the two-touchpoint governance boundary (GOV.PO.3 section on human interaction points) and should be its own, separately-decided follow-up if ever wanted, not bundled in silently here.

OUT OF SCOPE for this movement (flag anything that looks like it needs these, do not build them here): authentication/multi-user support (single local user, no need); a build toolchain/npm dependency; write/action buttons (see (G)); mobile responsiveness beyond basic usability; historical analytics/charts beyond the three-tier list. ACCEPTANCE-SHAPE GUIDANCE for whoever turns this into a formal SESSION_START: reproduce the existing terminal watch's exact data shape as the JSON API's baseline (backward compatible, AC-5-style), add targeted tests for the new stage-derivation function and the config read/write endpoint in isolation (no need to test the frontend JS with a browser harness -- test the data/API layer, same testing philosophy relay/NXS-LOCAL-0013 used for its own watch loop).

=== AMENDMENT 2026-09-08 (supersedes item (G) 'read-only, no action buttons' above; the rest of the original architecture research still stands as background) ===
Product Owner-directed correction after external design review: a monitoring-only dashboard is not enough. What's actually needed is an interactive PO + Orchestrator workbench that surfaces what is expected of the Product Owner, routes the Product Owner's answer to the correct session, and lets the work continue from the same screen. Reading the 'two-touchpoint' principle (work selection, design decisions) as 'therefore read-only UI' was wrong -- work-selection and decision buttons ARE the interface for those exact two touchpoints, and a screen that lets the Product Owner change the poll interval persistently is already not purely read-only anyway. The scope correction below, written as the amendment to hand directly to the implementing engineer session (English, verbatim):

Amend orchestrator_interactive_dashboard_app from a monitoring-only dashboard to an interactive PO + Orchestrator workbench.

Preserve the existing local stdlib backend and vanilla JS frontend. Reuse the orchestrator and local relay as the execution and decision sources; do not introduce another scheduler or independent state model.

First delivery must include:
- A human-action inbox, ranked by blocked work and urgency.
- Concurrent movement cards with process status, explicit work stage, last observed activity, owner, and next action.
- Movement detail: acceptance criteria, conversation, events, diffs, tests, artifacts, worktree/session references, and preview links.
- Start/resume of authorized work, queued messages to the correct session, and observable message-delivery acknowledgments.
- Structured execution requests with action ID, exact operation, working directory, expected effects, and blocker source.
- Automatic routing of already-authorized engineering actions away from the PO role; ask the human only for an actual missing decision.
- Serialized integration visibility and existing authorized auto-merge.

Do not infer work stage from Git dirtiness or heartbeat. Do not claim access to unavailable agent transcripts or hidden reasoning. UI actions must use existing authorization rules, reject stale requests, and prevent duplicate execution. Platform denials remain explicit.

Acceptance demonstration: Track five concurrent movements; answer a pending design question; deliver a message to the correct worker; route an authorized command request; resume the affected work; open its produced UI/test artifact. Complete this flow without manual chat-to-chat copying or Git commands.

DETAILED LAYOUT (from the same design review, informative -- the implementing session may adapt presentation but should preserve the five sections and their stated actions):
Main screen, five sections top to bottom: (1) 'Awaiting you' -- decisions, permission blocks, design questions; which work each one is blocking; actions: answer, approve an option, defer, reject. (2) 'Running movements' -- the concurrent movements, owner, real stage, last progress, next step; actions: open detail, send a message, request pause, stop. (3) 'PO agenda' -- suggested NEXT, ready work, dependencies, why each is waiting; actions: start, prioritize, queue. (4) 'Integration queue' -- PRs awaiting review/test/merge and why each is waiting; actions: view findings, request a fix. (5) 'Recently completed / archive' -- what shipped, test result, PR, remaining debt if any; actions: open the result and the artifact/UI that was built. A small summary strip above all five: e.g. '5 running - 2 awaiting decision - 1 in integration.' Any movement that needs a decision must surface at the TOP of its group, not just get sorted into 'active' generically.

Detail panel (opens on click, right-hand pane), six tabs: Summary (what's being done, user-facing benefit, acceptance criteria, next step); Live activity (the agent's own posted progress notes, running command/test, latest result); Conversation (PO/engineer/reviewer messages, threaded, showing which message answered which); Changes (changed files, diff summary, branch/worktree, PR link); Evidence (test result, screenshot, render output, local UI preview); History (dispatch, correction, decision, retry, and integration events in order).

'Where is Claude actually running' must be answerable via the relation agent/session -> movement -> worktree -> current activity -- surfaced explicitly, not hidden. If the platform does not expose it, never fabricate a full terminal transcript or hidden reasoning trace to fill the gap -- posted messages and tool events are what's real and what should be shown.

The single most valuable feature: an executable-request card. Convert a 'I can't run this in a terminal, no permission' message into a card shaped like: 'Test run blocked / Movement: .../ Requested action: .../ Target environment/worktree: .../ Expected effect: .../ Blocker source: PO role restriction / missing dependency / platform policy' with buttons [Route to engineer] [Run the authorized action] [Reject]. Three distinct cases must be told apart: (1) the action is already authorized but reached the wrong role -- the orchestrator routes it to the engineer automatically, no question surfaces to the Product Owner at all; (2) a genuinely new human decision is needed -- show the action and its effect, record the choice to the relay, let the affected work continue; (3) a platform/organizational policy is the actual blocker -- show the real blocker; a UI button must never be presented as if it can override that policy. The button must send a registered action id, not free-form shell text typed in the browser -- the backend resolves the id to its already-recorded operation, argument set, and working directory, which is what prevents running in the wrong worktree and prevents a double-click from starting the same thing twice; if the underlying command has changed since the id was issued, the stale approval must not apply.

Live stage must never be inferred from git dirtiness alone: a dirty worktree does not mean 'writing code' and a clean one does not mean 'done'. Show three distinct fields -- Process status (running / exited / disconnected), Work stage (review / coding / testing / awaiting PO / integration), Last observed activity (e.g. 'test started 90s ago') -- with stage sourced from real orchestrator/engineer-posted events, heartbeat limited to meaning process reachability only, and 'last activity unknown' shown honestly when there is no evidence, never a fabricated progress percentage.

A message box is itself part of the work: every movement needs a 'send a note to this work' field, and the message's own delivery state must be visible: Saved -> delivered to session -> received by agent -> answered. If delivery to the currently-running session isn't supported, queue it for the next continuation/resume call and say so explicitly in the UI -- never show 'Sent' for a message the agent never actually read.

Security note carried over from the architecture review: once action buttons exist, localhost-only binding is not enough by itself -- add a session token plus Origin/CSRF checking, specifically so another web page open in the same browser cannot silently send commands to the local service without an extra confirmation screen.

Explicitly deferred past the first delivery: a fully embedded terminal, desktop packaging, a drag-and-drop workflow editor, and advanced charting -- none of those block the acceptance demonstration above.

Success criterion for this whole screen, stated by the Product Owner directly: 'I understood what work is waiting on me, I gave the answer it needed, and I saw the work continue on the same screen.'

IN SCOPE, decided:
