# Check Point Gaia Embedded/Quantum Spark: exec channel rejected outright, needs interactive shell

status: planned · target: 

Root cause found by reading the pre-Java product's own real-fleet-proven Check Point configuration collector (Product Owner's direction, after two failed PTY/command-form guesses on the Java side): a Gaia Embedded/Quantum Spark device (e.g. the 1570/1590 line, confirmed live by the Product Owner: after PTY + a 4-form fallback deploy, the confirm's identity read still failed with EVERY exec-channel form timing out, exactly 4x30s) rejects the SSH exec channel outright -- it only accepts an interactive shell login (invoke_shell), never exec_command, regardless of the command sent. The pre-Java Python collector already had a proven fix: InteractiveSshSession, a persistent PTY-backed shell channel with prompt-learning and prompt-synchronized command dispatch, tried as the primary path with exec as a compatibility fallback for already-proven enterprise Gaia hosts.

Ported this to Java: new InteractiveShellSession (JSch ChannelShell-based, worker/transport/ssh), a new default DeviceTransport.execInteractive method (mirrors the existing fetchStreaming pattern -- only SshExecTransport overrides it, every other implementor/test double keeps compiling unchanged), and SshTransportSession now lazily owns one persistent interactive shell per connection, reused across calls. ConfirmCapabilityExecutor's identity/HA-peer reads now try the exec channel first (all 4 DeviceFirstContactCommandSet literal forms, unchanged from the prior fix, to avoid regressing the already-working fleet), then fall back to the SAME 4 forms over the interactive shell only if every exec attempt failed, timed out, or came back blank.

All worker/architecture-tests green, including a new end-to-end test proving the interactive fallback answers when the exec channel is rejected outright. Needs a fresh live re-test against the same real 1570/1590 device before this can move to done -- has NOT yet been confirmed against a real device, only against the ported logic's own unit test.

PO directive 2026-09-22: real-device confirm succeeded but took ~153s (four doomed exec-channel timeouts before the interactive-shell fallback ran). Fixed by threading the device's discovery-known model (already joined in JooqDeviceRepository.DEVICE_SUMMARY_SELECT from discovery_candidate.model, e.g. a Check Point Management Server's own hardware field) through WorkerClaimLoop -> ConfirmRequest -> ConfirmCapabilityExecutor: a recognized Spark/Gaia Embedded model now tries the interactive shell first, skipping the exec-channel attempts entirely, with the exec channel kept as a fallback in case the hint is wrong. Same closed command set either way, only trial order changes. Targeted + full worker/persistence/service/architecture-tests suites green.

Follow-up, 2026-09-22: the same exec-channel rejection that blocked confirm's identity read also starved inventory collection entirely -- a Spark/Gaia Embedded device confirmed (ENROLLED, 'Live') but returned zero interfaces/routes ('No interface evidence'). Fixed by adding the same interactive-shell fallback (already proven for confirm) to InventoryCapabilityExecutor's execOutput/execOutputPty, triggered only on ExecResult.ChannelFailed. Also fixed the frontend 'Live' badge (InventoryScreen.tsx, InventoryPanels.tsx) to require actual collected interface evidence, not just ENROLLED enrollment_state, since confirm succeeding was being read as full liveness. Worker/architecture-tests and frontend vitest suites green.
