# Local LDAP / Active-Directory group-membership authorization producer for D7, decoupled from the DEPLOY.1A server track

status: planned · target: docs/design/M14_LOCAL_LDAP_AUTHORIZATION_ARCHITECTURE.md -- DRAFT, discussion proposal, awaiting Product Owner review (relay/NXS-LOCAL-0024, 2026-09-08). Not implementation authority; freezing it would still not authorize dispatch.

Gives D7 (docs/design/CAPABILITY_STATE_VOCABULARY_AND_PRESENTATION.md section 3.3, FROZEN) a real actor-authorization producer without waiting for DEPLOY.1A's externally-blocked server/OIDC track: the operator binds to their own corporate Active Directory Domain Controller at --console launch and authorization is read from AD group membership. The draft resolves seven decisions (LD-1..LD-7): operator-credential bind through the existing DEV.2.1 env / <VAR>_FILE mechanism with a distinct variable namespace, never in a repo file, a URL or an argv; fail-closed on execution with AUTHZ_NOT_EVALUATED (never DENIED, never a silent downgrade to NO_APPLICABLE_AUTHORITY) when the directory is unreachable; in-memory process-lifetime state with a bounded re-validation interval and nothing persisted; per-action granularity as the eventual target with a single access group as the first slice; ldap3 over python-ldap for Windows/macOS operator-workstation portability; mandatory verified TLS; one bind at launch on the TTY, never from the browser. It leaves four named unknowns open (U-1 nested-group matching semantics needs Microsoft documentation before any freeze) and reports one authority contradiction for Product Owner resolution: the FROZEN LOCAL_CONTROL_PLANE_RUNTIME_AND_ENROLLMENT.md section 12 defines M14 as production OIDC/RBAC on a DEPLOY.1 prerequisite, so the draft recommends a distinct id (M14L) rather than amending a frozen row.
