# Render harness's happy-dom check failed under Bun (window.eval undefined)

status: automated_validated · target: before RB.5 (or any next UI build)

AUTOMATED_VALIDATED 2026-08-31 (contract: docs/history/phase/PHASE0_6_X_RENDER_HARNESS_HAPPYDOM_PIN.md). Root cause was NOT a happy-dom version regression as originally suspected 2026-08-30 -- it is a Bun/node:vm incompatibility. happy-dom executes each Window's script inside a node:vm context; under Bun that context's globals come back broken (window.eval is an own property whose value is simply undefined -- 'TypeError: window.eval is not a function' -- and even built-ins like Map/Error resolve to undefined inside a script run there). Reproduced identically on every happy-dom major tested (16.0.0, 19.0.2, 20.12.0) under Bun; the exact same happy-dom 20.12.0 works correctly under real Node.js (window.eval is a real function, normal global semantics) with zero code change to check-render.mjs. A dead-end explored and reverted before finding this: happy-dom's newer enableJavaScriptEvaluation setting does make document.write()-inserted <script> tags auto-execute without window.eval, but even that runs each script in its own isolated scope (top-level function/var declarations do not attach to window) -- not usable for this harness's needs (window.switchModule must be reachable), so that direction was abandoned, not shipped. Fix: tests/test_html_render_harness.py's _js_runtime() (renamed from _bun()) now prefers a real `node` binary and falls back to `bun` only if no Node is on PATH; docs/AI_DEVELOPMENT_PROTOCOL.md's documented command switched from `bun ...` to `node ...`. check-render.mjs itself is unchanged. bun.lock/package.json unchanged (bun install/package resolution was never implicated, only Bun's vm module). Evidence: tests/test_html_render_harness.py: 6 passed (was 5 passed/1 skipped when only bun was available) -- both the happy-dom and Playwright navigation checks now run and pass in this session's environment.
