## Summary

FROZEN, PO-approved architecture-only movement: a scope-limited (CLASS_0_CP_CONFIG_TARGET_SELECTION_ONLY), physical-entity-id-only candidate-selection-then-live-first-contact-confirmation design, gated by a new mandatory target-specific trust-lookup seam, storing the proven relationship in the already-approved M4 SQLite store via an additive migration that references (never copies) existing governed collector evidence and the registry's own revision signal for live currency checks. No PCP.1 amendment, no code, no schema change, no device contact, no support-bundle-key coupling in this movement.

## Risks forward

Architecture only -- no code path exists yet for any part of this design; M8.1 (relationship storage/API) is the next authorized movement, not yet started. The single-sourced (non-bidirectionally-corroborated) evidence limit and the operator_assertion dissent both remain open, carried forward from M6. Contradiction detection (serial-based) is explicitly DEFERRED pending a real measurement of CP config evidence retention duration that M8.3 must perform -- if retention proves too short, this design permanently lacks contradiction detection rather than fabricating one. The mandatory target-specific trust-lookup seam (M8.2) does not yet exist and gates M8.3. Whether console/registry_targets.py may import utils/cp_ssh_trust.py's new lookup directly or needs a vendor-neutral wrapper is an open implementation-shape question left to M8.4. Table/column names and migration version numbers remain illustrative, not frozen beyond the M8.1-M8.4/M7 ordering. Real-environment validation is required before M7 may target any relationship M8.3 produces, and is explicitly out of scope for M8.1/M8.2. The mapping_scope narrowing means this design, even once implemented, authorizes only CLASS_0 config-target selection -- it must never be read or extended as general device-identity proof without a separate, explicit PO decision.
