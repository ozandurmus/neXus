# restore_readiness_rb0 — RB.0 restore-readiness assessment (first implementation against the frozen Backup & Recovery contracts)

## Summary

User request: implement against the just-frozen docs/design/BACKUP_RECOVERY_CONTRACTS.md §5. New utils/restore_readiness.py: compute_restore_readiness, a pure function with no I/O, deriving per-device READY/STALE/PARTIAL/UNPROTECTED/UNKNOWN readiness from unified.json plus optional (currently empty, since RB.1-RB.3 do not exist yet) recovery_manifests and attestations maps. New main.py --restore-readiness-check CLI mode wired the same way as --render-only (registered in _MODE_PREREQUISITES/_require_bootstrap, requires a prior unified.json), writing data/state/restore_readiness.json. Zero network access, zero credentials, zero new device command -- matches the contract's own requirement that RB.0 be computable exactly like --repository-privacy-check.

## Evidence

- **automated**: 16 new tests in tests/test_rb0_restore_readiness.py (new pytest.ini 'recovery' marker): all five states; both evidence bases (held vs. device-attested, never merged, attestation alone never promotes to READY); VSX vs_id entity-id convention matching configuration/checkpoint_config_collector.py's _entity_id (<device>__vsid_<vs_id>, never the vsys label); cp+vsx -> checkpoint vendor, panorama -> panorama; a required-artifact-class gap caps state at PARTIAL even when a held artifact is otherwise validated/current; no_data inventory -> UNKNOWN (never UNPROTECTED, per the 'insufficient evidence vs. no recovery artifact' distinction in the contract); duplicate-row dedup; summary counts; a static no-I/O guard (no socket/requests/paramiko/getpass import). py -m pytest -q: 656 passed, 3 skipped, 2 pre-existing unrelated failures unchanged from baseline.
