# recovery_store_rb1 — RB.1 recovery-plane store: encryption, manifest, retention, validator (no collection)

## Summary

User request: implement RB.1 against the frozen docs/design/BACKUP_RECOVERY_CONTRACTS.md §2/§3/§8/§9. New utils/recovery_crypto.py (AES-256-GCM envelope encryption via the cryptography package, now pinned explicitly in requirements.txt instead of only a transitive paramiko dependency), utils/recovery_manifest.py (build_manifest/validate_manifest enforcing all five frozen §3 rules), utils/recovery_store.py (vault key resolution mirroring DEV.2.2's .support_hmac.key precedent -- the key lives on data_root, never on recovery_root -- plus write/read/decrypt-artifact and a consistency-group storage primitive), utils/recovery_retention.py (GFS plan_deletions as a pure function honoring the floor invariant, apply_deletions dry-run-by-default matching --storage-deduplicate's --apply convention). utils/runtime_paths.py gains resolve_recovery_root: SECURITYEXPERT_RECOVERY_ROOT, mandatory and absolute with deliberately NO OS-default (unlike runtime_root), validated separate from both the repository root and the runtime root via a generalized _validate_disjoint helper. main.py gains --recovery-store-check (offline diagnostic mirroring --persistent-secret-material-check) and --recovery-root. docker-compose.yml gains a securityexpert-recovery named volume mounted ONLY on worker, never nginx. utils/repository_privacy.py extended with the .enc suffix and a 'vault' forbidden root dir.

## Evidence

- **automated**: 41 new tests in tests/test_rb1_recovery_store.py (new pytest.ini 'recovery' marker, shared with RB.0) covering every §9 security invariant assigned to RB.1: 9.1 (a real write_artifact call, then every file under recovery_root is grepped for an unmistakable plaintext marker -- none found, confirming ciphertext-only on disk including the atomic-write temp path), 9.2 (the vault-key resolver rejects a data_root nested under recovery_root), 9.4 (a real support bundle built via support_bundle.run_support_bundle alongside a populated recovery store contains none of its bytes, checked by unzipping and scanning every member), 9.5 (scan_repository flags a probe .enc file and a vault/ root dir), 9.6 (validate_manifest rejects a non-null restore block), 9.9 (a 200-iteration seeded-random property test over arbitrary fleets/policies: retention never reduces an entity below its configured floor, and never deletes the sole remaining is_rma_grade artifact even when it is nominally over the tier limit), 9.11 (docker-compose.yml and docker-compose.prod.yml parsed by indentation to isolate the nginx service's own lines, comments stripped, and asserted to never mention 'recovery'). Plus manifest-builder derivation rules (pan_running_config always is_rma_grade=false, pan_device_state/cp_gaia_backup always true, known_gaps auto-filled and rejected-if-empty for classes with documented vendor exclusions), crypto round-trips (encrypt/decrypt, wrap/unwrap) and two tamper-detection cases (wrong key, flipped ciphertext byte) both raising RecoveryCryptoError, vault-key persistence across a simulated restart (two independent get_or_create_vault_key calls against the same paths), and CLI integration through main.main() including the mandatory-env-var failure path. py -m pytest -q: 697 passed, 3 skipped, 2 pre-existing unrelated failures unchanged from baseline. Repository privacy gate: PASS / 0.
- **manual_cli**: python main.py --recovery-store-check exercised directly against throwaway SECURITYEXPERT_RUNTIME_ROOT/SECURITYEXPERT_RECOVERY_ROOT: initializes vault/groups/retention under the recovery root, generates and persists the vault key at <data_root>/.recovery_vault.key (confirmed on disk, physically separate from the recovery root), prints only the key's opaque fingerprint (never the path or key bytes), reports zero artifacts held. The missing-SECURITYEXPERT_RECOVERY_ROOT and nested-inside-runtime-root cases both fail closed with actionable, value-free error messages (exit 2). docker compose config (base file and the docker-compose.prod.yml overlay) confirms the volume topology: worker mounts both securityexpert-runtime and securityexpert-recovery; nginx mounts only securityexpert-runtime.
