# registry_keyed_job_targets — M6 -- Registry-keyed job targets, Option D fail-closed admission shell

## Summary

PO decision 2026-09-06 (bounded nexus-decision-council synthesis, Option D only): config_refresh_cp now resolves console-submitted device_id targets against the PCP.1 Device Registry at admission (POST /api/jobs) and again immediately before execution (console/runner.py), fail-closed. This is a targeting foundation, not functional per-device collection -- every otherwise-eligible target still refuses with UNSUPPORTED / IDENTITY_TRANSLATION_REQUIRED, since no legitimate device_id -> collector entity_id relationship producer exists yet. No PCP.1 relationship write, no M4 schema/table change, no new durable mapping store, no frozen-contract edit; operator_assertion stays an OPEN dissent. Do not claim this build DONE as a working device-targeting capability.

## Evidence

New console/registry_targets.py::resolve_registry_targets(device_ids, *, data_root) -- the one shared fail-closed function both admission call sites use: unknown device_id -> UNKNOWN_DEVICE_ID; known but not in an eligible lifecycle state (only ENROLLED_UNVERIFIED is eligible; DISABLED/RETIRED/CONTACT_VERIFIED/OBSERVED are not) -> DEVICE_NOT_ELIGIBLE; known and eligible -> IDENTITY_TRANSLATION_REQUIRED (unconditional -- no translation producer exists). ## Risks forward

Actual per-device cp-config collection remains non-functional: no code path can ever build a config_refresh_cp argv carrying a device_id (or any translated entity_id) today, because resolve_registry_targets() refuses every non-empty target set unconditionally (unknown/ineligible/registry-unavailable are all fail-closed refusals; the sole eligible+known case still refuses with IDENTITY_TRANSLATION_REQUIRED). The next real capability step needs a legitimate device_id -> collector entity_id relationship producer (a distinct, separately-authorized movement) before this admission shell does anything but refuse. M7 is deliberately not named as this record's roadmap 'next' -- its viability and the identity-evidence producer/M8 sequencing return to Product Owner review; operator_assertion (inferring the mapping from endpoint/hostname/display-name/vendor-hint/spelling equality) remains an OPEN dissent and must not be treated as accepted mapping authority without a later explicit PO decision naming it so.
