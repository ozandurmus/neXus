# parallelize_full_regression_execution — DEV.TEST.1 -- Parallelize local and GitHub Actions full-regression execution

## Summary

Replaced the GitHub Actions full-regression job's serial `python -m pytest -q` (measured 11m56s, workflow run 34016204567) with `python -m pytest -q -n auto --dist worksteal`, proven green on a real push-to-main run (workflow run 34020356372): 4 workers, 1944 passed / 38 skipped / 0 failed in 275.74s (4m35.74s). Final Product Owner-directed CI topology (same-session correction): `pull_request` schedules `validate` only, `full-regression` runs exclusively via explicit `workflow_dispatch` -- no automatic trigger on pull_request or push to main, and the workflow's `push:` trigger is removed entirely (it would otherwise produce an empty, zero-job run). Pure test-execution infrastructure, no product behavior change, M3 not started.

## Risks forward

The full-regression job's parallel step measured 4m36s on GitHub-hosted infrastructure, ~36s above this movement's 4-minute acceptable ceiling, due to a small number of tail tests dominating wall-clock time after the bulk of the suite finishes in under a minute (see evidence). Not a correctness or coverage gap (0 failed, every test executes, single aggregate exit code), and a genuine ~61%/2.6x improvement over the 11m56s serial baseline either way -- but a real, reported bottleneck, not silently accepted as meeting the preferred target. A narrowly scoped future follow-up could identify and address the specific slow tail test(s) (likely retry/backoff-timing-bound, not xdist-distribution-bound) if tightening below 4 minutes becomes a priority; out of scope for this movement, which already replaces an 11m56s serial gate. The in-session YAML-syntax misdiagnosis (attributing a simple parse error to an environment/automation-identity limitation) is itself a risk-forward lesson: any future session touching this workflow file should run tests/test_ci_workflow_fast_pr_regression.py::test_workflow_yaml_parses (or `python -c "import yaml; yaml.safe_load(open(path))"`) locally before push, since this defect class produces no readable error anywhere in the GitHub UI -- only a silent zero-job failing check suite that looks identity/branch-related until someone actually parses the file. M3 (nav_3_capability_state_vocabulary) remains not started and is now_next.next again, unchanged by this movement. full-regression now has no automatic trigger at all (workflow_dispatch only) -- there is no post-merge integration safety net beyond validate's fast gates unless a session explicitly dispatches it for a materially justified reason; this is intentional Product Owner policy, not an oversight.
