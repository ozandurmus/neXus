# local_control_plane_metadata_store — M4 -- Local control-plane metadata store (approved Option A)

## Summary

Added the additive local SQLite control-plane metadata store under RuntimeRoot data_root, owning only job definitions, job/run lifecycle records, schedules, capability projections, idempotency/submission metadata and control-plane runtime metadata. Storage infrastructure only: no job behaviour, target resolution, runner, scheduler, enrollment, HTTP/UI surface or device contact, and the PCP.1 Device Registry stays filesystem JSON and unmigrated.

## Evidence

Schema version 1, seven tables (schema_migrations, control_plane_metadata, job_definitions, job_submissions, job_runs, schedules, capability_projections), all STRICT. SQLite runtime: journal_mode=WAL, synchronous=FULL (chosen over WAL's usual NORMAL because CON.0 section 7.9 requires a job record durable before the runner may start it, and NORMAL can lose a committed record on power loss), foreign_keys=ON, explicit busy_timeout=5000ms, all read back from the engine rather than assumed. Migrations are explicit, monotonic and one-transaction-per-version; a failure rolls its own version back and leaves earlier versions applied. Fail-closed typed outcomes for invalid placement, unsupported/newer schema (naming encountered and supported versions), corruption or non-database content, failed migration, bounded contention timeout and uniqueness/foreign-key violation; corrupt files are left byte-for-byte untouched, never repaired, recreated, downgraded or discarded. Uniqueness: idempotency_key is the job_submissions primary key, and a partial unique index enforces at most one active run per durable job definition. Ownership boundary proven against the real schema -- a test walks every column of every table and fails on any endpoint/address/credential/secret/token/trust/raw-config/backup/CAS fragment; targets are stored only as opaque device_id or logical_entity_id references, never a copied endpoint. Capability projections persist only D2-D6 dimension values, basis/run information, semantic identity and producer/support-rule context plus every consumed authority generation (AC-CS-71) and an identity_mapping_proven flag (AC-CS-97); primary_status, qualifiers, evidence presentation, shell composition, affordances, action declarations, taxonomy and authorization state have no column and are test-enforced absent. Privacy extended, not duplicated: the store lives at data_root/state/control_plane.db, outside the data/runs/* subtree run_support_bundle enumerates, so bundle exclusion is structural and support_bundle.py was not modified; .db/.db-wal/.db-shm were already DATABASE_ARTIFACT in the privacy gate and already gitignored, and the store is now registered LOCAL-SENSITIVE (CLASS 2) in PRIVACY_AND_DATA_HANDLING.md. Added a ninth evidence_backend concern selector that refuses postgres explicitly, naming pcp_storage_engine as still open -- SQLite is not the production engine (AC-ST-7). Validation: 57 focused tests in tests/test_m4_control_plane_metadata_store.py plus 161 passed / 9 skipped across architecture, privacy-gate, PCP.1 registry, support-bundle, CON.2 console-job, evidence-backend and runtime-paths suites. Automated tests do not prove production readiness or real-environment validation; no device was contacted. PO correction round (one bounded round, same branch): the migration ledger is now validated as an EXACT PREFIX of MIGRATIONS rather than by max(version) alone -- a ledger carrying the supported version under a foreign migration name, an unknown lower or extra version, a gap, a non-prefix sequence, or an unreadable foreign column set is refused with the typed schema-version outcome naming the encountered ledger and highest version and the supported ledger and version range. Duplicate and out-of-order entries are structurally impossible in this build's own ledger (version is an INTEGER PRIMARY KEY, so rowid is the version) and are refused where they are representable, in a foreign unkeyed ledger table; both shapes are tested. Open order was corrected so every refusal precedes every persistent mutation: connection-local busy_timeout/foreign_keys, then the corruption probe, then ledger validation, and only then WAL activation, synchronous=FULL, ledger creation and pending migrations -- so a refused database keeps its journal mode, its ledger and its table set and grows no -wal/-shm sidecars. Connection cleanup is deterministic: _connect closes its own handle if configuration fails and the open sequence closes on BaseException, proven by tracking every connection the module creates across configuration-failure, corruption and ledger refusals. Focused tests 57 -> 74.
