# ui2_b0_extraction_tooling — UI2 B0/B0-9 -- extraction tooling (Line-1 Python): Private Replay tokenizer over an evidence/capture directory, C6-layout fixture set, shape-preserving encoding

## Summary

New scripts/ui2_extract_fixtures.py implements docs/design/UI2_0_C6_CAPABILITY_EXTRACTION_CONTRACT.md section 3: reads every *.json file under a capture directory, tokenizes it through one utils.support_bundle.Tokenizer session (cross-output identity equality), writes section 3.4 provenance metadata (fixture_id, capability_id, command_tuple, vendor_version, capture_date, fixture_kind, capture_session_id, source_capture_path) with SYNTHETIC/DERIVED marking only when the caller explicitly asks, and stages fixtures in a temp directory that utils.repository_privacy.scan_repository (the same offline gate main.py --repository-privacy-check runs) must pass before anything is copied into --output-dir; a failing scan raises FixtureDLPRefusalError and writes nothing. Closes C6 section 7 open item 1 by adding Tokenizer.shaped_token(kind, value) to utils/support_bundle.py -- a new method beside the existing token()/network_token() (not a parallel competing tokenizer) that classifies a value's shape (ipv4/hex/digit/alnum/opaque) and HMAC-derives a same-shape, same-length replacement, so a serial's length/character class survives tokenization instead of collapsing to the generic SERIAL_<14 hex> form.

## Risks forward

This is the tool only, not a real extraction -- B1-5 (first Extract movement) is the first real use against checkpoint/scripts/cp_inventory.sh + checkpoint/cp_runner.py per C6's queue row 1, and may find the CLI's one-command-tuple-per-invocation shape (chosen for simplicity; a multi-command capture session runs the tool once per command sharing --capture-session-id) needs widening once real capture-directory shapes are known. shaped_token's shape classifier (ipv4/hex/digit/alnum/opaque) does not yet cover every C6-named preserved property -- cluster/context membership and ordering (C6 section 3.3) are proven by Tokenizer's existing determinism and the extraction script's payload-order-preserving sanitizer, not by a dedicated new test in this movement; a future movement exercising a real multi-context/ClusterXL capture should confirm this explicitly. The extraction-specific sensitive-key extension (EXTRACTION_SENSITIVE_KEYS) currently names only appliance_serial/serial_number/sn; B1-5 will likely need to extend it with real field names once real capture JSON shapes are seen.
