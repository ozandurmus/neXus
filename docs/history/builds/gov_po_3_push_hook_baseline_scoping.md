# gov_po_3_push_hook_baseline_scoping — GOV.PO.3 -- push-hook baseline scoping: block only genuinely new privacy findings

## Summary

Fixes the live bug found during GOV.PO.3 AC-5 demonstration 1 (relay/NXS-LOCAL-0012 seq 3-4): scripts/nexus_engineer_tool_gate.py's pre-push privacy gate ran scan_repository() against the full working tree and failed closed on ANY finding, including pre-existing repository debt (two prose false positives in project/build_history.json and relay/NXS-LOCAL-0003-...json), blocking an unrelated one-file push and every orchestrated push thereafter. The hook is now baseline-aware: it scans the working tree, and only when that scan is non-empty also scans the movement's own recorded base commit (via `git archive` into a throwaway tempdir, reusing scan_repository() unmodified -- no new scanning code path) and blocks only findings absent from that baseline. Findings are matched on (path, rule, a sha256 fingerprint of the flagged line's stripped content), not (path, exact line number), so a pre-existing finding whose line shifted from unrelated earlier edits still counts as pre-existing. A denial names only the genuinely new finding(s).

## Risks forward

The baseline scan resolves report.git.base via `git merge-base HEAD <base>` and exports that commit with `git archive`; a movement whose .nexus/approved_task.json is missing or whose base ref cannot be resolved locally degrades to treating the working-tree scan as authoritative with no baseline credit (documented as 'baseline unavailable' in the pass/deny reason) rather than failing the hook itself -- unchanged from today's behavior in that case, not a regression, but also not exercised by the synthetic fixtures here beyond the missing-approved-task path implicit in _approved_task_git_base's own None-returning branches.
