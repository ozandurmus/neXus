# cp_remote_collection_done_marker_diagnostics — CP remote collection - DONE-marker-loss diagnostic hardening

## Summary

A real run hit RuntimeError('CP remote collection ended without DONE marker') with exit_status=0. First pass (this build's original commit) aligned checkpoint/cp_runner.py's _run_remote_collection channel-drain loop with checkpoint/direct_ssh_probe.py's tight-drain idiom and added safe diagnostic fields (exit_status/processed_gw/total_gw/stderr_bytes/last_marker) -- did not resolve the recurrence, but the new fields (processed_gw=0, total_gw=None, last_marker=None, stderr_bytes=658) proved the channel-drain race was NOT the cause and located the failure to before checkpoint/scripts/cp_inventory.sh line ~94 (TOTAL_GW is never even echoed), with real stderr output the code was discarding. Second pass: captures a bounded (8192-char) in-memory stderr sample and classifies it into safe, non-identity-bearing category tokens (no_such_file_or_directory, command_not_found, permission_denied, not_a_tty, unbound_variable, syntax_error, connection_reset_or_broken_pipe, or unclassified) via _classify_stderr_sample() -- the raw sample is discarded immediately after classification, never logged or raised (AGENTS.md raw-evidence law). Both the DONE-marker-missing and nonzero-exit-status RuntimeErrors now report stderr_classification alongside stderr_bytes. Root cause remains UNKNOWN -- still not a confirmed fix -- but the next real run will report which category of error is actually occurring instead of only a byte count.
