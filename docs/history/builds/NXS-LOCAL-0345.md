# NXS-LOCAL-0345 — Failover engine phase C: controlled manual execution under CLASS 2 invariants

## Summary

Implemented at-most-once command submission, two-sided JIT precondition re-check, ClusterXL and PAN HA executors behind a server-owned pilot fence, and sticky OUTCOME_UNKNOWN quarantine. Added the M3 Operations screen.

Status corrected to blocked on 2026-09-20 under NXS-LOCAL-0347. Two independent external reviews of the Failover Engine, Phases A-D, both returned a final verdict of REJECTED: docs/design/CODEX_FAILOVER_ENGINE_FINAL_REVIEW.md and docs/design/CLAUDE_FAILOVER_ENGINE_FINAL_REVIEW.md. The commits that followed those reviews (FailoverPilotAllowlist bean declaration, @Autowired annotations, Flyway autoconfiguration exclusion) are dependency wiring and do not address the named P0 defects. Four items of the eight-item required P0 closure set were re-verified against the source on 2026-09-20 and remain open: (1) the baseline digest is computed once at creation in BaselineSnapshotSummary and never recomputed when a schedule is loaded or dispatched, so a party able to write to the database can substitute baseline_json and keep the old digest; (3) the DELIVERY_UNKNOWN guard in FailoverExecutionService sits inside the not-successful branch, so a successful result carrying DELIVERY_UNKNOWN bypasses quarantine and enters normal post-verification; (4) RETURN_TO_SERVICE evaluates only the postA observation against the recovered-role allowlist and never evaluates postB, so the claim of two-sided affirmative verification does not hold; (5) FailoverKeyManagementService generates and persists a fresh master key when the key file is absent instead of failing closed to ABORTED_KEY_UNAVAILABLE, so key loss presents as tampering across every existing schedule. Items 2, 6, 7 and 8 (transactional coherence, ledger canonicalization and multi-instance booking concurrency) were not assessed in this pass and are recorded as UNKNOWN rather than closed. Containment as observed on 2026-09-20: FailoverExecutionService gates on isClusterAllowed(clusterRef) first and FailoverPilotAllowlist seeds only cls-uuid-cp, cls-uuid-pa and cls-01, none of which match the live fleet's cluster reference form, so no live cluster can reach execution today. That fence is itself compiled into a constructor rather than being configuration or a recorded Product Owner enrolment, its member sets carry AIView pseudonyms of real fleet devices, and its authorizedBy value is a string literal with no traceable decision behind it.
