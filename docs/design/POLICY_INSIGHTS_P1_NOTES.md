# Policy Insights P1: Check Point Insights tab — implementation notes

Status: DOCS (implementation notes, not a contract). Authority: `POLICY_INSIGHTS_DESIGN_2026_11_24.md` (FROZEN, PO 2026-11-24) and its decision record, section 9 phase P1 only. Masked names only.

## What P1 ships

- `GET /api/v2/policy/policies/{id}/insights?type&grade&page&days` and `GET .../insight?insightId=` (one wildcard per route, as the route tests require), `POLICY_READ`, GET-only, no device contact, nothing stored. A package of another vendor answers `supported=false`.
- `PolicyInsights` (service): reads `PolicyHygiene` verdicts and findings and the `PolicyDomainIndex` object rows. It runs no analysis of its own; no log intake, no reorder, no proposal (P2+).
- Policy tab **Insights** (`?screen=policy&tab=insights`), second tab of the Judge group: package counts, insight list with type/grade filters, detail view.

## Insight rules

| Type | Source in the existing engines | Grade |
| --- | --- | --- |
| I1 | `REDUNDANT` (one earlier rule covers all four selectors) | PROVEN |
| I2 | `CONFLICT` | PROVEN (never matches; intent is a human question) |
| I8 | `disabled` finding | PROVEN |
| I9 | `expired` finding; "Schedule evidence is incomplete" | PROVEN; NOT_EVALUABLE |
| I10 | `unused` finding (zero hits, old last hit) | INDICATED; SUPPORTED only with a measured window >= threshold |
| I11 | domain index `unused` (management report) / no stored reference and no report | PROVEN / INDICATED (lower bound) |
| I12 | domain index duplicate groups (equal type and values) | PROVEN |

- Every PROVEN insight carries `INSTALL_STATE_NOT_VERIFIED`.
- **SUPPORTED is not reachable in production in P1.** Stored hit counts carry no window start (design F9) and Check Point cluster aggregation is not established, so every I10 is INDICATED. `PolicyInsights.analyze` takes a per-rule measured window so the section 3.1 rule is one tested condition; phase P3 (counter samples) feeds it. Until then the service passes none.
- Missing or invalid counters (UNKNOWN findings) produce no I10; they are counted as `hitsMissing`.
- I11/I12 are domain-wide (scope `domain`): where-used counts span every package of the management domain.

## Package counts (design 3.2)

Over enabled security rules (NAT rulebase and disabled rules left out and reported as `outsideSecurityRules` / `disabledRules`, so the Hygiene tab's all-rule coverage is their sum with `rules`).

- `decided`: shadow status other than UNKNOWN.
- `upToWithLogs` = `decided` + rules whose only blocking reason is log-resolvable. A ceiling.
- The rest by reason, each reason classed once in `PolicyInsights.reasonClass`: LOGS (user/category, time/content, application overlap, application default ports), COLLECTION (snapshot incomplete, time/zone/install-on evidence not collected), everything else NOT_RESOLVABLE. A reason nobody classified is NOT_RESOLVABLE. A rule behind an earlier unreadable rule takes that rule's own reason.

## AIView

New response keys are projected by `PolicyPrivacy` through closed vocabularies (`insightType`, `evidenceGrade`, `insightNeeds`, `insightCaveats`, `insightScope`, `insightRole`, `reasonClass`); rule names go through the existing rule pseudonyms; evidence strings are `PolicyHygiene.EVIDENCE`.

## Detail panel and change list (PO 2026-11-25)

- A row (click, Enter, Space) opens the detail in a right-side drawer, full width on a small screen; Esc / Close returns focus to the row, which stays highlighted.
- The panel shows one headline sentence per type (I1, I2, I3, I4, I8, I9, I10, I11, I12), the involved rules side by side (every covering rule marked "Decides first", every overlapping earlier rule "Overlapping earlier rule", the shadowed rule "Never reached" or "Partly shadowed") and the suggested actions. Highlighted cells are the ones the engine's verdict rests on: position, source, destination, service / application, install-on and action for I1/I2/I3/I4 (when proven); the enabled flag for I8; the schedule for I9.
- `GET .../insight` carries one more key, `ruleObjects`: the objects the involved rules' cells and reference extras name (id, name, type, status; no members or values), the same projection the rule detail carries, masked by `PolicyPrivacy` the same way. No new route and no new action id.
- Actions by type: I1 remove / disable instead; I2 review intent / move above the covering rule (never a remove; the move is shown as not verdict-safe); I3 like I1 when PROVEN with `coverAction=SAME` (remove / disable instead with "No behaviour change"), or review intent / disable instead when a covering rule has a different action or calls an inline layer; I4 narrow rule / reorder above overlapping rules (never a one-click remove, always "Behaviour may change" until I7 verifies reorder safety); I8 remove; I9 remove / extend schedule; I10 disable for one window with logging on (Q5); I11 remove object; I12 merge. The grade never hides an action: PROVEN makes the strong action the main button, any other grade shows it with that grade's warning. Only a PROVEN I1 or PROVEN same-action I3 is labelled "No behaviour change" (design section 4).
- **No action writes to a device** (Q7). A button adds one line to the package's change list (one planned change per insight; another choice replaces it). The list is browser state (`localStorage`, key per package and per masked / unmasked view so names written by one view never show in the other), with a text and a CSV export.

## P2a: G1 engine and union cover (I3)

Implementation notes, not a contract. Authority: the same FROZEN design (sections 3, 4 I3, 6.1, 6.4, 7, 9 phase P2) and decision record (Q3, Q8, Q9). Check Point only; steps b (partial shadow I4) and c (safe reorder I5/I7, reorder-only proposal) are not started.

- **G1 engine** `PolicyRegion` (service, pure). A box is the product of the four selectors the shadow engine resolves (source, destination, service, application). A dimension is a union of ranges per family, or everything except such a union (`any` = everything). Families are opaque keys; the universe holds every family, so a distinct key never makes a region smaller than it is. `residual(subject, earlier, budget)` returns the effective region "match minus the union of earlier matches" as disjoint boxes plus the earlier boxes that took part. It is PROVEN (exact) or NOT_PROVEN with "analysis budget". Opaque tokens (Palo Alto application-default and application identities) have no box.
- **I3** `PolicyUnionCover`. Subjects are enabled rules the shadow engine did not find REDUNDANT or CONFLICT.
  - Earlier rules come from the shadow engine's own `EvaluationScope`, so nothing crosses a layer (Q9).
  - Only readable rules with a compatible placement (same install-on) take part. Unreadable rules (user, application, time, unresolved) are fixed anchors (Q3): they never cover and are never subjects. They cannot weaken a proven cover.
  - COVERED needs two or more earlier rules. A set where one rule alone covers is I1/I2 and is left to the shadow engine.
  - A snapshot with collection failures evaluates nothing (design 3.1 "rule-complete").
  - Budgets: the shadow engine's (`RULE_WORK` 1,000,000 per rule, `TOTAL_WORK` 200,000,000 per snapshot).
- **Grades.** COVERED gives a PROVEN I3 that lists the covering set and carries `INSTALL_STATE_NOT_VERIFIED`. The action relation goes into the evidence string and `counter.coverAction`: `SAME`, `DIFFERENT` (intent is a human question, as for I2) or `INLINE_LAYER`. NOT_PROVEN gives an I3 graded NOT_EVALUABLE with `counter.unionReason` "analysis budget", never a cover.
- **Package counts are unchanged.** They stay the shadow engine's, so the P1 check "counts equal the Hygiene tab" still holds. An I3 on a rule the shadow engine left UNKNOWN is not counted as decided. This is open for a PO decision.
- **Routes and UI.** No new route, no new action id. `GET .../insights` adds `unionCover` (evaluated, covered, notProven, notEvaluable by reason) to measure how often the budget is hit (Q8). The service caches the I3 pass for each snapshot instance. The Insights tab gains the I3 type filter, a union-cover line, and detail with every covering rule and the action relation.
- **AIView.** New evidence strings are `PolicyInsights.EVIDENCE`; `coverAction` and `unionReason` are closed vocabularies in `PolicyPrivacy`.
- **Tests.**
  - `PolicyRegionDifferentialTest`: residuals against brute-force enumeration over a tiny universe; small budgets give NOT_PROVEN and never a wrong PROVEN.
  - `PolicyUnionCoverDifferentialTest`: random Check Point rulebases with anchors and disabled rules. I3 must equal the brute-force union cover exactly, and every single-rule cover must be REDUNDANT/CONFLICT in the shadow engine.
  - `PolicyUnionCoverTest`: fixtures for actions, anchors, layers, install-on, an incomplete snapshot, budget, route and AIView.
  - `PolicyUnionCoverScaleTest`: 10,000 rules, about 1.4 s warm on a laptop JVM, no budget hit.
- **Real-environment validation (open).** No real package has been analysed. The design's P2 check (the firewall team reviews proposed moves) comes with step c. Before then, a sample of I3 insights on one real package should be checked as aiview against the vendor console.

## P2b: partial shadow (I4)

Implementation notes, not a contract. Authority: the same FROZEN design (sections 3, 4 row I4, 7, 9 phase P2) and decision record (Q3, Q8, Q9). Check Point only. Step c-1 (I7 safe reorder) is built (section P2c-1 below); step c-2 (I5 merge, the reorder-only proposal) is open. Chosen as the next P2 step because no further self-contained P1 step is left.

- **`PolicyPartialShadow`** (service, pure) runs on the G1 engine of step a and shares `PolicyUnionCover.Earlier`, the earlier-rule bucketing (now package-private, not copied). Subjects are enabled, readable rules of a rule-complete snapshot that the shadow engine did not mark REDUNDANT or CONFLICT and that I3 did not find COVERED. Earlier rules are the readable rules of the same `EvaluationScope` with a compatible placement; nothing crosses a layer (Q9) and unreadable rules are fixed anchors that never take part (Q3). Budgets are I3's (`RULE_WORK`, `TOTAL_WORK`).
- **PARTIAL** needs an earlier rule whose box really shares a point with the subject (a span test alone is not enough) and a proven non-empty rest from `PolicyRegion.residual`. A rule the earlier rules cover wholly has no I4. The overlapping list is every intersecting earlier rule, including one another earlier rule already hides, in rule order.
- **Decided here: same action only.** The insight exists only when EVERY intersecting earlier rule has the subject's action. One intersecting rule with another action means a promote there could change a verdict (I7 territory): no I4, and the rule is counted in `partialShadow.differentAction`, never shown. An Apply Layer rule, on either side, is never the same action. Rules that do not intersect the subject do not matter.
- **Budget (Q8).** Running out of work is NOT_PROVEN ("analysis budget"), shown as an I4 graded NOT_EVALUABLE with `counter.partialReason`, never as a partial. If an earlier rule of a scope ran out of its own work window before it was read, a later subject of that scope that would be PARTIAL is NOT_PROVEN instead: the unread rule might cover it or have another action. A rule left unread for being unreadable (an anchor) is not such a gap.
- **Insight.** `I4`, PROVEN, scope "package", `INSTALL_STATE_NOT_VERIFIED` like I3. Rules: the subject, then the overlapping earlier rules (role `overlapping`), capped at `PolicyInsights.MAX_OVERLAPPING` (10); `counter.overlappingRules` is the total and `counter.moreOverlapping` the rest. The fixed evidence string says the overlap is proven and says nothing about moving, safety or behaviour. The Insights tab shows the fixed sentence "Part of this rule's match is decided by earlier rules with the same action; its zero or low counter can be explained by them."
- **Package counts are unchanged** (the shadow engine's), so the P1 check "counts equal the Hygiene tab" still holds. I4 is not counted as decided; this is the same open PO note as for I3.
- **Routes and UI.** No new route, no new action id, no device command, no migration. `GET .../insights` gains `partialShadow` (evaluated, partial = the I4 insights, differentAction, notProven, notEvaluable by reason) to measure how often the budget is hit. The service caches the I4 pass for each snapshot instance, as for I3. The Insights tab gains the I4 type filter, the measurement line and the detail.
- **AIView.** Nothing is free text: the evidence strings are `PolicyInsights.EVIDENCE`; `partialReason` (closed set shared with `unionReason`) and the role `overlapping` are closed vocabularies in `PolicyPrivacy`; the rest are references and counts.
- **Source-port families.** `PolicyRegion` treats two distinct family keys as disjoint, which is conservative for covers but not for overlaps. Source-port families exist only in the Palo Alto resolver, so this does not affect Check Point. It must be revisited before I4 is extended to Palo Alto.
- **Tests.**
  - `PolicyPartialShadowDifferentialTest`: random Check Point rulebases in one or two layers with anchors, disabled rules and mixed actions. The PARTIAL set, the overlapping lists and the same-action flag equal a brute-force enumeration exactly; small budgets give NOT_PROVEN and never a wrong PARTIAL; no I1/I2/I3 rule and no different-action overlap has an I4.
  - `PolicyPartialShadowTest`: fixtures for one and two overlaps, a hidden overlap, a different-action overlap, Apply Layer, anchors, layers, install-on, an incomplete snapshot, another vendor, the cap, budget, the route and AIView.
  - `PolicyPartialShadowScaleTest`: 10,000 rules, about 1.1 s warm on a laptop JVM, no budget hit.
- **Real-environment validation (open).** No real package has been analysed; nothing here is REAL_ENV_VALIDATED. The firewall team reviews a sample of I4 insights on one real package as aiview against the vendor console before the grade is relied on.

## P2c-1: safe reorder (I7)

Implementation notes, not a contract. Authority: the same FROZEN design (sections 2 G3, 3.1, 4 row I7, 6.1, 6.4, 7 Check Point, 9 phase P2) and decision record (Q2, Q3, Q7, Q8, Q9). Check Point only. Step c-2 (I5 merge candidates, the reorder-only proposal object and change board export) is open. Chosen as the next P2 step because no further self-contained P1 step is left.

- **G3 `PolicyEffectSignature`** (service, pure). Verdict part: action and `inline-layer` (`PolicyPartialShadow.sameAction`, so an Apply Layer rule equals nothing). Profile references: the snapshot model's `profile-setting/*` extras. The Check Point mapper stores none on an access rule (design F21 and section 7 name profile and log settings for Palo Alto), so on mapped Check Point data the part is empty and equal on every rule. Log setting: the track type (`Rule.log()`) plus the `track-*` extras. A part the snapshot did not collect (track type `UNKNOWN`, blank or absent; every part but the verdict for a vendor not mapped here) is UNKNOWN and equals nothing, another UNKNOWN included.
- **`PolicyReorder`** (service, pure). Candidates are the I4 rules (`PolicyPartialShadow` PARTIAL with `sameAction`): design 6.1 step 2. The move is "r to just above B", B being the first rule of r's I4 overlapping list (the earliest earlier rule of the same `EvaluationScope` and install-on that r really intersects). The pass walks the same `EvaluationScope` as I3/I4 with its own per-scope rule list (anchors included), so nothing crosses a layer (Q9).
  - **Refused and counted, no insight**, checked in this order: an anchor between B and r (unreadable: user, application, time, unresolved object, auto-generated, opaque; or an Apply Layer rule), even one that looks disjoint (Q3) → `anchorBlocked`. B in another section than r → `crossesSection`: crossing a section is a user choice the design keeps for later, not offered here. An enabled rule between them that overlaps r with another verdict effect → `unsafeDifferentEffect`. Disabled rules are skipped.
  - **Install-on of a crossed rule.** Equal to r's: it takes part. Proven disjoint (`PolicyNormalization.disjoint`: two distinct atomic resolved gateways): it takes no part ("disjoint"). Anything else (a group, "Policy Targets", any) is not provably disjoint and takes part as if it were equal (fail-closed). This is stricter than "different install-on takes no part": a rule on "Policy Targets" can match the packets of a rule on one gateway. Since the I4 pass compares equal install-on only, this is the one way an I4 rule meets an overlapping crossed rule with another action.
  - **Offered**: `SAFE` when B and every overlapping crossed rule have r's full signature: PROVEN, evidence "no behaviour change". `SAFE_INSPECTION_CHANGES` when the verdicts agree but one of them differs in profile or log setting, or the part was not collected (Q2): PROVEN for the verdict, "verdict-safe, inspection changes", never "no behaviour change".
  - **Symbolic check (design 6.4)**, by `PolicyRegion` intersect and minus, never enumeration: r's box intersected with B and each taking-part crossed rule, each part given to the first of them that matches it today. Rules before B decide the same packets in both orders and no readable rule of r's placement meets r before B, so this region holds the true one (an upper bound where an anchor or a not provably disjoint placement before B takes part of it). `EQUIVALENT` when every part is decided today by a rule of r's full signature; `CHANGES` with counts only (`changedRules`, `changedBoxes`; no range is stored or returned); `NOT_PROVEN` with the reason. `SAFE` implies `EQUIVALENT`; the engine asserts it. A `SAFE_INSPECTION_CHANGES` move can be `EQUIVALENT` when the differing crossed rule decides none of r's match today: the label stays the conservative one.
  - **Budget (Q8).** The shadow engine's (`RULE_WORK` per rule and per move, `TOTAL_WORK` per snapshot). Running out, or a rule between B and r left unread for it, is NOT_PROVEN ("analysis budget"): an I7 graded NOT_EVALUABLE, never a move.
  - **One move at a time.** Each candidate is evaluated alone against the stored order; moves are not stacked in this step (design 6.1 asks the proof of a later move to read the result of the earlier ones, which needs the proposal object of step c-2).
- **Insight.** `I7`, scope "package", after I4 in the display order. Rules: the promoted rule (`subject`), B (`promoteAbove`), then the crossed rules (`crossed`), capped at `MAX_OVERLAPPING` with `crossedRules` and `moreCrossed`. Counter: `reorderResult`, `equivalence`, `decidingRules`, `changedRules`, `changedBoxes` and `crossedProof` (for B and each listed crossed rule: `ruleId`, `crossedReason` "disjoint" or "same verdict effect", `inspectionChanges`). PROVEN moves carry `INSTALL_STATE_NOT_VERIFIED`; `raiseGrade`/`needs` NONE. Fixed evidence strings in `PolicyInsights.EVIDENCE`, one each for SAFE, SAFE_INSPECTION_CHANGES and the budget.
- **Package counts are unchanged** (the shadow engine's), the same open PO note as I3/I4.
- **Routes and UI.** No new route, no new action id, no device command, no migration; no action writes to a device and no command text is generated (Q7). `GET .../insights` gains `safeReorder` (evaluated, safe, safeInspectionChanges, unsafeDifferentEffect, anchorBlocked, crossesSection, notProven, notEvaluable by reason; the six results sum to `evaluated`). The service caches the I7 pass per snapshot instance like I3/I4. `GET .../insight` returns the crossed rules through the existing `rules`/`ruleObjects` projection. The Insights tab gains the I7 filter (label "Promote (proven reorder)"), a measurement line, the two suggestion wordings, and a detail with "Decides first today", the crossed rules, the proof per rule and the fixed caveat "One move against the stored order; moves are not combined. No command is generated". The change list item reads "Move rule #r above rule #B". An I7 is never shown green and never as a bare "safe".
- **AIView.** Roles `promoteAbove` and `crossed`, `reorderResult` (offered results only), `equivalence`, `crossedReason` and `reorderReason` are closed vocabularies in `PolicyPrivacy`; the proof carries rule ids, closed words and booleans; rule names go through the existing pseudonyms.
- **Tests.**
  - `PolicyReorderDifferentialTest`: eight seeds, 1,760 random Check Point rulebases in one or two layers, a layer sometimes in two sections, with time/unresolved/Apply Layer anchors, disabled rules, mixed actions, profiles, log settings and three install-on placements. A brute-force oracle evaluates every packet of the universe per gateway before and after every move, with anchors matching or not: SAFE changes no verdict and no full effect, SAFE_INSPECTION_CHANGES no verdict, no move across an anchor, a section or an overlapping rule of another verdict is offered, the reported deciding rules equal the oracle's changed-deciding-rule set (a superset where the region is an upper bound) and EQUIVALENT agrees. Small budgets give NOT_PROVEN and never a result the full budget does not give. About 2.6 s.
  - `PolicyReorderTest`: fixtures for the plain move, disjoint and same-effect crossed rules, a different-action crossed rule (UNSAFE), anchors, Apply Layer, profile and log differences, UNKNOWN parts, a section boundary, install-on, an incomplete snapshot, another vendor, the cap, the budget, the route and AIView.
  - `PolicyReorderScaleTest`: the 10,000-rule policy of the I3/I4 scale tests: 21 I4 rules, 21 moves, all SAFE, no budget hit, about 0.2 s warm on a laptop JVM.
- **Real-environment validation (open).** No real package has been analysed; nothing here is REAL_ENV_VALIDATED. Design section 9's P2 check: the firewall team reviews twenty proposed moves on one package (as aiview, against the vendor console) before the grade is relied on. Open question for that review: whether a Check Point access rule carries an inspection or logging setting the mapper does not collect (it would belong in the signature).

## P2c-2a: merge candidates (I5)

Implementation notes, not a contract. Authority: the same FROZEN design (sections 2 G2/G3, 3.1, 4 row I5, 6.3, 6.4, 7 Check Point, 9 phase P2) and decision record (Q2, Q3, Q7, Q8, Q9). Check Point only. Step c-2b (the reorder-and-merge proposal engine and change board export) is open.

- **`PolicyMerge`** (service, pure). Walks the same `EvaluationScope` per section as `PolicyReorder`, skipping disabled rules (`Boolean.FALSE.equals(Rule.enabled())`; an unknown `null` enabled state stays an anchor). Evaluates every adjacent pair `(a, b)` of enabled rules inside one proven scope and one section.
  - **What is built (`MERGE_CANDIDATE`).** Both rules are fully readable (no anchor), share the same install-on placement both ways (`PolicyNormalization.compatible` in both directions) and the same full effect signature with no `UNKNOWN` part (`PolicyEffectSignature.sameFull`; an `UNKNOWN` part equals nothing, another `UNKNOWN` included), and have `PolicyRegion.Box` matches that are equal in three dimensions and differ in one without `a` already covering `b`. The surviving rule `a` keeps its identity, position, name and comment (design 6.3); the merged cell in the one differing dimension is the union of both rules' references, and the engine verifies before offering the pair that the merged rule normalizes to a box equal to `box(a) U box(b)`.
  - **What is refused and counted, no insight**, checked in this order:
    - `anchorBlocked`: either rule is an anchor — user, application or time constraint, unresolved object, `auto-generated` flag, missing/unresolved install-on, opaque selector (`Box.of` null), Apply Layer rule, or a negated cell (fail-closed reading, design F5: Check Point negates the whole cell, so combining two negated cells would take their intersection by De Morgan's law rather than their union).
    - `differentInstallOn`: install-on placements are not mutually `compatible`.
    - `differentEffect`: action, inline layer, present profile references, track type or `track-*` extras differ, or a signature part is `UNKNOWN`.
    - `alreadyShadowed`: `a`'s box already covers `b`'s in every dimension (equal boxes, or `b` a subset of `a` in the differing cell), so `b` is already an I1 (`REDUNDANT`, same action) and stays there.
    - `differsInSeveralCells`: boxes differ in two or more dimensions.
  - **Budget and containment (Q8).** Uses `PolicyUnionCover.RULE_WORK` and `TOTAL_WORK`. Running out of work, or an internal-invariant breach on one pair, turns that pair into `NOT_PROVEN` (`notProven` counter; emitted as an `I5` graded `NOT_EVALUABLE` with `mergeReason` `"analysis budget"`), never a candidate and never a failed response. Other vendors, snapshots with collection failures, incomplete snapshots and sections with unproven rule order evaluate nothing and report enabled security rules in `notEvaluable`.
  - **What is not built in this step.** Pairs separated by an enabled rule (even a disjoint one), pairs across a section header, and pairs that would become adjacent only after an I7 promote are not offered here: design row I5 allows "movable to adjacent by I7", and the proposal engine of the next step is what combines moves. Chains `(a, b, c)` where all three are mergeable emit the adjacent pairs `(a, b)` and `(b, c)` without building multi-rule groups. No vendor command script is generated (Q7).
- **Insight.** `I5`, scope `"package"`, between `I4` and `I7` in `PolicyInsights.TYPES`. `PROVEN` carries `INSTALL_STATE_NOT_VERIFIED`, `raiseGrade`/`needs` `NONE`, and fixed evidence `PolicyInsights.I5_MERGE` ("no behaviour change for the verdict and the log setting of stored management intent (profile settings are not collected for Check Point)", worded identically to `I7_SAFE`). Rules: surviving rule `a` (`subject`) then `b` (`merged`). Counter: `mergeResult` (`MERGE_CANDIDATE`) and `differingCell` (`source` | `destination` | `service` | `application`), counts and closed words only — no ranges, no addresses, no concatenated names or comments (both rules' names and comments are shown separately through the existing rule projection).
- **Package counts are unchanged** (the shadow engine's), the same open PO note as I3/I4/I7.
- **Routes, caching and UI.** No new route, no new action id, no device command, no migration. `GET .../insights` gains `merge` (`evaluated`, `candidates`, `alreadyShadowed`, `differsInSeveralCells`, `differentEffect`, `differentInstallOn`, `anchorBlocked`, `notProven`, `notEvaluable` by reason; the seven pair outcomes sum to `evaluated`). `PolicyQueryService` caches the I5 pass per snapshot instance beside `reorderCache` with the same 4-entry bound and `hygieneSlots` semaphore. `GET .../insight` returns the pair through the existing `rules`/`ruleObjects` projection. The Insights tab gains the I5 filter ("Merge candidate (adjacent rules)"), measurement line, suggestion wording, side-by-side detail highlighting the differing cell, and change-list action `"Merge rule #b into rule #a"` (labelled `"No behaviour change"` only when `PROVEN` and paired with the Check Point profile caveat; never a green chip, matching I7).
- **AIView.** `mergeResult`, `differingCell`, `mergeReason` and role `merged` are closed vocabularies in `PolicyPrivacy` (anything else reads `"UNKNOWN"`); `I5_MERGE` and `I5_BUDGET` are in `PolicyInsights.EVIDENCE`; rule and object names go through the existing pseudonyms.
- **Tests.**
  - `PolicyMergeDifferentialTest`: eight seeds, 1,760 random Check Point rulebases across two layers, two sections, anchors, disabled rules, mixed actions, profiles, log settings (`UNKNOWN` included) and four install-on placements against a brute-force packet-universe oracle per gateway (verdict and full effect unchanged, merged box equals the union of the two boxes, small budgets give `NOT_EVALUABLE` and never a false candidate).
  - `PolicyMergeTest`: fixtures for one-cell merges on source/destination/service, chains, equal/covered boxes, multi-cell differences, action/log/profile/`UNKNOWN` signature differences, install-on differences, anchors (time, unresolved, user, auto-generated, Apply Layer, negated cell), disabled vs enabled rule between, section and layer boundaries, another vendor, incomplete snapshot, budget and invariant-breach containment, route JSON and AIView.
  - `PolicyMergeScaleTest`: the 10,000-rule Check Point policy of the I3/I4/I7 scale tests: 9,999 adjacent pairs evaluated, 0 candidates, 0 already shadowed, 6,000 differing in two or more cells, 3,999 differing in effect, 0 differing in install-on, 0 anchor blocked, 0 not proven (no budget hit), about 48 ms thread CPU time (`CpuTimeGuard`) with a 4x growth ratio guard against 2,500 rules (~3.4x).
  - `PolicyInsightsMerge.test.tsx`: filter chip, measurement line, non-green chip rule, side-by-side detail with differing cell, profile caveat, change-list item and budget state.
- **Real-environment validation (open).** Nothing here is `REAL_ENV_VALIDATED`. Design section 9's P2 check — the firewall team reviewing twenty proposed moves on one real package (as aiview, against the vendor console) — stays open and now includes the merge pairs.

## P2c-2b: reorder-only proposal (engine)

Implementation notes, not a contract. Authority: the same FROZEN design (sections 2 G6, 3.1, 6.1, 6.4, 7 Check Point, 9 phase P2) and decision record (Q2, Q3, Q8, Q9). Check Point only. Engine only: `PolicyProposal` (service, pure, package-private) is called by tests and by nothing else; no route, no UI, no storage, no export, no migration, no device command and no command text (Q7: a human-readable change list comes first).

- **What is built.** `PolicyProposal.propose(stored, subjects, workLimit, ruleLimit)` takes the stored snapshot and the subject rule ids in the order the caller wants them tried; `allOfferedMoves(stored)` takes every I7 candidate of the stored order (one per I4 rule, in rule order, offered alone or not: a refusal against the stored order does not bind the stacked order).
  - **Per step, the current order.** The I3/I4 pass and `PolicyReorder.analyze` run on the in-memory snapshot (the stored one plus the accepted moves so far). The subject's move is accepted only when its result is SAFE or SAFE_INSPECTION_CHANGES, then applied with G6 before the next subject is read. The analysis of an unchanged snapshot is reused, so a refusal costs no new pass; an accepted move forces one.
  - **Refused, counted, snapshot untouched, next subject still tried.** The engine's own `UNSAFE_DIFFERENT_EFFECT`, `ANCHOR_BLOCKED` (Q3) and `CROSSES_SECTION` (Q9). `NO_LONGER_A_CANDIDATE`: the subject is no I4 rule of the current order (an earlier move made it redundant or covered, or it overlaps another action; also an id that is no rule, or one listed twice). Only `r to just above B` as `PolicyReorder` defines it is ever tried: never across a layer or a section, never across an anchor, never another scope.
  - **G6 `reordered`.** Builds the snapshot after one move: only that one section's rule list changes; metadata, objects, failures, the other sections and every rule outside the moved stretch are the stored instances. The stored snapshot is never mutated.
  - **`Rule.number`.** It is order to the Check Point layer check (`CpLayers.advance` requires strictly increasing numbers inside a layer, else the layer is "earlier sections not analysed" and no subject is evaluated); `PolicyHygiene` and the insight projection only report it, and the NAT evaluator is another rulebase. So the moved stretch is renumbered by position: the slot keeps its number and the rule in it changes, which keeps the section's number set, its first and last number and the continuation into the next section. A test shows the unrenumbered swap is "unproven" and the renumbered one is not. The proposal therefore carries slot numbers; a rule's stored number is read from the stored snapshot by rule id.
  - **One shared budget (Q8).** One pool of `workLimit` units (default `TOTAL_WORK`, `ruleLimit` per rule, default `RULE_WORK`) is passed to every `PolicyReorder` pass of the proposal. The I3/I4 passes keep the stored pass's own full budget, so the candidates are the stored pass's. A step that is `NOT_PROVEN` (pool or window used up, a crossed rule left unread, or an internal check) is recorded with the reason "analysis budget", every remaining subject is recorded `NOT_PROVEN` the same way, and the run stops: never a silent skip, never an accepted move that was not proven. A limited run is therefore a prefix of the full run and never accepts a move the full run refuses (differential test). The only change to `PolicyReorder` is an overload that takes the caller's `Budget`; the existing signatures delegate to it.
  - **Result** (counts and closed words, no range, address, name or comment): per step the subject and B rule ids, the result (an offered word when accepted, else a refusal word), accepted, the step's equivalence, the crossed-rule count and the inspection flag; for the package `packageVerdict`, `label`, `accepted`, `refused` by reason (every reason present), `inspectionChanges`, `budgetStopped`, `emptyReason` and the final in-memory snapshot (for the later replay and export steps).
  - **Package verdict (design 6.4).** `EQUIVALENT` only when at least one move was accepted and every accepted step is; `CHANGES` when an accepted step changes the deciding rule of some part (only a SAFE_INSPECTION_CHANGES step can); `NOT_PROVEN` when the budget stopped the run; `NO_MOVES` when nothing was accepted. Equivalence composes: a step that keeps every packet's full effect against the order before it keeps it against the stored order. Any accepted SAFE_INSPECTION_CHANGES step labels the package "verdict-safe, inspection changes" (Q2); "no behaviour change" is only ever the label of an EQUIVALENT package of SAFE steps, and the profile caveat of I7 applies to it unchanged.
  - **Empty proposals.** Another vendor ("unsupported rulebase"), a snapshot with collection failures ("snapshot collection incomplete") and a snapshot with no subject ("no offered move") give no step and the stored instance, never an exception.
- **Not built.** A route; the change list from the proposal; export; replay with logs; merges (I5) inside a proposal; stacked proofs across sections (a move that crosses a section stays refused); a move other than "r above B"; replay of a proposal against a later stored snapshot (the proposal is bound to the snapshot instance it was made from).
- **Cost.** Without scope-local passes one accepted move cost one whole I3/I4/I7 pass (about 2.4-3.0 s CPU for 10,000 rules): the 21 accepted moves of the scale policy cost about 50 s CPU. Since 2026-11-26 (scope-local passes, next bullet) an accepted move re-analyses only the evaluation scope (layer) it touched. Measured, thread CPU time on a laptop JVM: the 10,000-rule scale policy is ONE layer, hence one scope, so it gains nothing: 21 accepted moves still cost 45-49 s CPU (ratio to 21 whole passes 0.8-1.1, as before), and the reuse costs nothing measurable. The same rules cut into five layers of two sections, with five I4 pairs planted per layer (27 accepted moves): 4.2 s against 18.4 s for the whole-snapshot passes on the same snapshot, ratio 0.23 (the layers were analysed 6, 8, 6, 6 and 5 times instead of 28 each). The gain is about (1 + moves / layers) / (1 + moves) and exists only for a package of several layers whose moves fall in different ones; inside one layer a later step still re-reads the layer (what a rule is compared with is every earlier rule of its layer), and a move in one section re-reads that layer's later sections too.
- **Scope-local passes (2026-11-26, engine only, no API change).** `PolicyProposal.propose` after an accepted move analyses again only the scope the moved section belongs to; `PolicyProposal.proposeReference` keeps the whole-snapshot passes at every step and is the oracle. Result, steps, package verdict, label, refusal counts and the final snapshot are identical for every input and every work limit. What makes that exact, not approximate (details in the `ScopeLocal` comment):
  - A scope is a contiguous run of sections sharing one `EvaluationScope` state (nothing crosses a layer, Q9). The scope-local path applies only when every section's place in the order is proven, each scope is one contiguous run, and each scope alone reads as one proven state; an unproven order, a layer seen again or an inline layer give whole-snapshot passes at every step (`Stats.scopes == 0`).
  - I3/I4 (fresh budget per pass, `TOTAL_WORK`): each scope runs on its own sections with `TOTAL_WORK / scopes` units from a cold object memo and is used only if no unit was refused anywhere (`Budget.refused`, a probe on the calling thread). The whole snapshot's charge is then at most the sum, which fits the pool, so the whole pass refuses nothing either and its verdicts do not depend on the budget. Else the step is a whole pass. The object memo can change a verdict only through the group nesting depth limit, so groups nested deeper than 20 switch the scopes off.
  - I7 (one shared pool for the whole proposal, Q8): the pool is charged what the whole pass charges. A scope's I7 pass runs with the object memo the scopes before it leave (seeded, so every unit is charged as in the whole pass; without the seed the work-limit sweep fails), its charge is recorded, and a step charges the sum to the pool. If the pool would run out inside the step or any unit was refused, the step is the whole pass on the real pool, so the stop point of every work limit, the NOT_PROVEN prefix and "never accepts what the full run refuses" are the whole pass's.
  - No static state and no cache outlives one `propose` call; the stored snapshot is never mutated. Only seams: `Budget.refused()` plus a thread-local probe (changes no charge), and `PolicyReorder.analyze` over a caller-owned resolver for one scope.
- **Tests.**
  - `PolicyProposalTest`: no candidate, a SAFE move, the inspection label, a refusal that leaves the snapshot alone and does not stop the next subject, anchor and section refusals, two constructed stackings (a move SAFE alone against the stored order that is refused after an earlier move, and one refused alone that is SAFE after an earlier move), `NO_LONGER_A_CANDIDATE`, the shared budget stopping mid-proposal (swept over every work limit), another vendor, an incomplete snapshot, the stored snapshot untouched, G6 identities and slot numbers.
  - `PolicyProposalDifferentialTest`: 1,280 random Check Point rulebases (one or two layers, anchors, disabled rules, mixed actions, profiles, logs, three install-on placements), each proposed in rule order and in a random order and subset; a brute-force packet oracle per gateway compares the original with the final snapshot: a SAFE-only proposal changes no verdict or full effect, any proposal changes no verdict, no anchor, layer or section is crossed, EQUIVALENT agrees, the numbers stay strictly increasing, and small budgets stop with `NOT_PROVEN` and never accept what the full budget refuses.
  - `PolicyProposalScaleTest`: the 10,000-rule policy: 21 steps, 21 accepted, all SAFE; thread CPU time against the rounds it ran times one measured pass (a ratio, not a wall-clock constant; limit 1.5, measured 0.8-1.1: one layer, no gain). A second case, the same rules in five layers with planted pairs, compares the scope-local proposal with the whole-snapshot passes on the same snapshot: equal result, ratio 0.23, limit 0.5.
  - `PolicyProposalScopeLocalDifferentialTest`: the scope-local proposal against `proposeReference` on the 1,280 rulebases of `PolicyProposalDifferentialTest`, on 900 multi-layer, multi-section ones (moves in one layer, candidates in another), in rule order and in random order and subset, over every work limit 0..1199 of three fixed fixtures and a random sweep of work limits and windows; an unproven order falls back with the same result. `PolicyProposalScopeLocalTest`: the per-scope run counters (a move in layer one never analyses layer two again; a move in one section still analyses the layer's later sections, shown by a refusal naming the new first overlapping rule; one layer is one scope).
- **Real-environment validation (open).** No real package has been analysed; nothing here is REAL_ENV_VALIDATED and nothing is wired to a route or screen. Design section 9's P2 check (the firewall team reviews twenty proposed moves on one package as aiview, against the vendor console) must run over a proposal, not over single moves, before a package verdict is relied on. Next step: a route and the change list over the proposal, then I5 merges inside it.

## P2c-2d: merges inside the proposal (engine)

Implementation notes, not a contract (automated validation only; nothing is `REAL_ENV_VALIDATED`). Authority: `POLICY_INSIGHTS_DESIGN_2026_11_24.md` (FROZEN) section 4 row I5, section 6.1 point 4, section 6.3 and section 6.4, and `PO_DECISION_RECORD_2026_11_24_POLICY_INSIGHTS.md` (Q2, Q3, Q7, Q9). Check Point only, engine only: `PolicyProposalMerges` (service, package-private, pure; no existing production file edited, no device command, no command text, no migration).

- **What is built.** `PolicyProposalMerges` runs `PolicyMerge.analyze` on `PolicyProposal.Result.snapshot()` (or a stored snapshot directly), so pairs that become adjacent only after proven reorder moves are offered (design 6.3). Accepted `MERGE_CANDIDATE` steps are applied one at a time via G6 (`merged`): the surviving rule keeps its id, uuid, number, name and comment; the merged rule is removed; the differing cell becomes the order-preserving, de-duplicated union of both cells (`negated=false`; negated cells stay anchors); `PolicyMerge.analyze` re-runs after each accepted merge so chains `(a, b, c)` merge as `(a+b)` then `(ab+c)` only when the second pair remains `MERGE_CANDIDATE` in the updated snapshot, under one shared `Budget` (`PolicyMerge.TOTAL_WORK` / `RULE_WORK`; any unprovable step is `NOT_PROVEN` with `"analysis budget"` and stops the run as a prefix of the full run). Steps and results carry rule ids, counts and closed words only (no range, address, name or concatenated comment), the stored snapshot is never mutated, and `combine(PolicyProposal.Result, merges)` yields `EQUIVALENT` only when the reorder part is `EQUIVALENT` or `NO_MOVES` and every accepted merge is proven (`NOT_PROVEN` if either stopped on budget; the label stays the reorder part's label, or `"no behaviour change"` for an equivalent merge-only package). Covered by `PolicyProposalMergesTest`, `PolicyProposalMergesDifferentialTest` and `PolicyProposalMergesScaleTest`.
- **Not built.** Route wiring, a change-list line for a merge inside a proposal, export, replay with logs, and Palo Alto.
- **Real-environment validation (unchanged, open).** Automated validation only; nothing here is `REAL_ENV_VALIDATED`. Design section 9's P2 check on a real package (as aiview, against the vendor console) stays open.
