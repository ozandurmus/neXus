# Check Point and Palo Alto failover readiness checks

**Status:** DRAFT -- proposal for Product Owner review; not implementation authority.

## What exists today (ten lines)

1. The Java `PreflightRegistry` has 13 registered checks and required CP/PAN manifests; `CheckResult` already carries a check ID, status, enforcement, summary, and observed time.
2. `PreflightService` builds a two-member `ClusterEvidenceSnapshot` from enrolled devices and their latest inventory, then evaluates it; its report cache lasts five minutes and is not durable check history.
3. The service currently substitutes constant sync, policy, interface, resource, and other health values, so those fields are **not** measured readiness evidence.
4. Member role can come from inventory or `observedHaRole`; the peer role is deliberately `UNKNOWN` until independently corroborated.
5. `OperationsScreen` groups enrolled members by cluster reference, offers per-cluster GET/POST preflight, and renders check rows from the API.
6. Its fleet table shows `NOT EVALUATED` until that browser session reads a cluster; the Product Owner reports 40 clusters in this state, while the screen computes its count from enrollment.
7. `UI2_0_FAILOVER_ENGINE_ARCHITECTURE.md` marks Phase A implemented/ratified and later phases draft/roadmap; later-phase Java classes also exist, but neither fact approves these new reads.
8. `FAILOVER_READINESS_IN_THE_JAVA_PRODUCT_2026_09_15.md` is DRAFT analysis; `FAILOVER_ENGINE_ARCHITECTURE.md` is a gated design whose §10.2 supersedes conflicting earlier action statements.
9. Existing inventory gate rows cover CP `cphaprob stat`, `cphaprob -a if`, VSX variants, and the direct PAN HA-state XML API; they do not establish same-pass readiness semantics.
10. Queue items for CP command gates, readiness contract, reciprocal agreement, VSX/VSLS, and PAN Active/Active remain planned; readiness is evidence, never authorization.

## Reading rules for both tables

These are **candidate** read-only checks, not runnable instructions. Every row means a direct, identity-verified read of **both** members in one collection pass, with one run ID, per-member collection outcome and observed time. A peer field reported by member A does not replace a read from member B. Compare opaque identities locally and publish only masked names and derived relationships. `PASS` needs both observations and a proven vendor interpretation; `FAIL` needs an explicitly observed adverse condition; missing, failed, unsupported, contradictory, or semantically unproven evidence is `UNKNOWN` (mapped to the existing `INSUFFICIENT_EVIDENCE`, `COLLECTION_FAILED`, `NOT_EVALUABLE`, or `UNSUPPORTED` status). A positively established unsupported mode is not a healthy result. Thresholds, equivalence rules, and field meanings below are **proposals** until a frozen contract, official vendor semantics, and approved real-device evidence establish them. No command below is approved for execution by this document.

Gate legend: **Listed** means the exact key is signed off in `ui2/capability-registry/src/main/resources/capabilities/gate_registry_fixture.yaml` for its *existing* inventory/configuration purpose; the readiness parse scope, frequency, context, and same-pass reuse still need gate review. **Needs PO approval** means no matching signed-off key was found for that exact read/context; an approved command gate row and semantic validation are prerequisites. Expert commands run in Expert; Gaia Clish requires an explicit `clish -c` from Expert. PAN's listed reads use the direct firewall XML API, not Panorama or an unapproved CLI transport.

## Minimum infrastructure proposal

1. Keep `PreflightRegistry`, `CheckResult`, `PreflightReport`, the preflight API, and the Operations check table. First remove the fabricated healthy facts in `PreflightService.buildSnapshotForCluster`; unavailable evidence must yield an explicit insufficient/unknown state. This is a future implementation prerequisite, not a change in this draft.
2. Add **one read job per logical cluster** through the existing authenticated CP SSH / direct PAN XML API paths. Resolve canonical member identities server-side, collect both members in one pass, bind every fact to run ID, member, source/context and observed time, parse only safe fields in memory, then discard raw output. If either member fails, preserve the partial pass but never score it as a two-sided PASS. VSX parent and per-VS units share the physical member pass while keeping VSID attribution distinct.
3. Reuse `CheckResult` for each check's `PASS`/`FAIL`/insufficient outcome and observed time; add a durable per-run, per-cluster check-result store only because the current five-minute service cache and browser-session cache cannot answer fleet-wide last-evaluated/history queries. Persist safe derived statuses and provenance, not raw vendor responses. Any schema migration needs its own approved contract and application-role grants.
4. Serve the latest stored **display** result to the existing Operations › HA & readiness cluster rows, with per-check status, why, source coverage, and observed time. `NOT EVALUATED` changes only after a real two-member read job has produced an attributable check result; collection failure displays `UNKNOWN`/`COLLECTION_FAILED`, not a green result. Keep a separate on-demand fresh pass for any future action decision: persisted display readiness never authorizes failover.
5. Keep A/P and classic ClusterXL as the first battery. Show VSX parent and per-VS results separately only where semantics are established; keep VSLS and PAN A/A fail-closed pending their open decisions. No browser-origin command, new credential path, executor, or device write is proposed.

## Product Owner decisions (2026-09-27)
Recorded from the Product Owner's answer; the rest of this document stays DRAFT.
1. **When the checks run:** immediately before a failover, fresh, as part of the failover request; a failover is
   performed only if they are suitable at that moment (matches queue item `failover_recheck_on_request`). A displayed
   result is never the decision.
2. **Continuous active/standby monitoring:** valued -- the PO wants active/standby watched continuously, e.g. over SNMP.
   SNMP is a new transport and credential type for neXus; it needs its own design (SNMP version, v3 credentials in the
   credential store, the OIDs per vendor, polling interval) and PO approval before implementation.
3. **Vendors:** evaluate the same way for every vendor where the data can be captured -- FortiGate and Cisco ASA
   included, not only Check Point and Palo Alto.
Open (still for the PO): which checks are blocking in the first release, and which new device reads are approved
(questions 1, 2, 4-6 above).

## Product Owner decisions (2026-09-27, second answer)
Recorded from the Product Owner's answer to questions 1, 3 and 4 and the SNMP design question.
1. **Blocking:** every check in this battery is blocking. A FAIL or UNKNOWN on any check means "do not fail over";
   there are no advisory-only rows in the first release. (Rows whose semantics are unproven therefore block until
   proven -- fail-closed, consistent with the UNKNOWN law.)
2. **Cadence:** a periodic readiness pass every 4 hours, plus the fresh pass immediately before any failover
   (decision 1 of the first answer). One SSH session per member per pass; the checks run one at a time, in order,
   inside that session, with an optional configurable pause between checks.
3. **VSX:** a VSX Virtual System failover is its own failover step, independent of the chassis (physical member)
   failover. Per-VS readiness (CP-08) belongs to the VS failover step; CP-01..CP-07 belong to the chassis step.
4. **SNMP monitoring** (later work, not this battery): optional per device; the poller must support SNMP v1, v2c and
   v3 (the PO's own estate uses v3). Polling around once a minute. Its own design (OIDs per vendor, credential-store
   types for communities and v3 users) comes before implementation.
Still open: question 2 (which new device reads enter the command gate) -- each new read needs its own PO approval of
the exact command before it is implemented; and question 6 (field-semantics evidence).
