### A. Root Cause Analysis

1. **Does removing `BASH_ENV` break the recursion regardless of the unpinned last link?**
   - **Yes, once `unset BASH_ENV` has executed**, because non-interactive `bash` invocations (such as `#!/bin/bash` in `/bin/is_scalable_platform.sh`) only auto-source the startup file named by `$BASH_ENV` (and `/root/.bash_profile` does not export `ENV`). Without `BASH_ENV`, non-interactive child `bash` processes do not read `/root/.bashrc` → `/etc/bashrc` → `/etc/profile.d/*.sh`, breaking the cycle before any startup script runs ([`INCIDENT_2026_11_11_MDS_FORK_STORM.md`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/INCIDENT_2026_11_11_MDS_FORK_STORM.md#L64-L80)).
   - **Caveat in Option 1 (`bash -lc 'unset BASH_ENV; <cmd>'`):** `unset BASH_ENV` runs **after** the outer `bash -l` has already sourced `/etc/profile` and `/root/.bash_profile` (which sets `BASH_ENV=$HOME/.bashrc` on line 11 and then sources `~/.bashrc` on lines 7–9). On 2026-11-11, the outer login shell survived startup because `/etc/profile` loaded `.CPprofile.sh` *before* `/root/.bash_profile` set `BASH_ENV`, satisfying `.CPprofile.sh`'s load guard ([`INCIDENT_2026_11_11_MDS_FORK_STORM.md`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/INCIDENT_2026_11_11_MDS_FORK_STORM.md#L87-L91)). If a future Check Point JHF adds an unguarded bash helper call to `/etc/bashrc` or `/etc/profile.d/*.sh`, Option 1 would loop *during* `/root/.bash_profile` before reaching `unset BASH_ENV`.

2. **What could still recreate the loop after the fix?**
   - **Child login shells inside `mds_backup`:** Any script inside `$CPMDIR/scripts/mds_backup` or its child tools (`gtar`, domain backup scripts, `su -`, `bash -l`, `bash --login`) that starts a login shell will re-read `/root/.bash_profile` and re-export `BASH_ENV=/root/.bashrc` for its subtree ([`INCIDENT_2026_11_11_MDS_FORK_STORM.md`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/INCIDENT_2026_11_11_MDS_FORK_STORM.md#L96-L98), [`MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md#L37-L38)).
   - **`csh` startup files:** `mds_backup` is a `csh` script ([`INCIDENT_2026_11_11_MDS_FORK_STORM.md`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/INCIDENT_2026_11_11_MDS_FORK_STORM.md#L68)). If any `/etc/csh.cshrc`, `/root/.cshrc`, or Check Point `.CPprofile.csh` / `MDSprofile.csh` script sets `setenv BASH_ENV` or spawns `bash -l`, the variable returns.
   - **Interactive SSH shells (`SSH_INTERACTIVE` / `openShell`), which the fix contract misses completely:** When neXus opens an interactive PTY shell on an Expert-mode Check Point device, `sshd` starts `/bin/bash` as a login shell (`-bash`), which reads `/root/.bash_profile` and exports `BASH_ENV=/root/.bashrc`. All MDS interactive inventory/policy reads (`cpinfo -y all`, `cplic print`, `cplp list`, `mgmt_cli` in [`InventoryCapabilityExecutor.java`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/ui2/worker/src/main/java/com/securityexpert/nexus/ui2/worker/inventory/InventoryCapabilityExecutor.java#L1808-L1844) and [`gate_registry_fixture.yaml`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/ui2/capability-registry/src/main/resources/capabilities/gate_registry_fixture.yaml#L3338-L3352)) and gateway failover `FramedShell` reads ([`CpFailoverJobExecutor.java`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/ui2/worker/src/main/java/com/securityexpert/nexus/ui2/worker/failover/CpFailoverJobExecutor.java#L533-L566)) execute inside an interactive login shell with `BASH_ENV=/root/.bashrc` set, because they do not use `bash -lc` and never run `unset BASH_ENV`.

### B. Option 1 vs Option 2, and Literal / Quoting Pitfalls

1. **Option 1 (`bash -lc 'unset BASH_ENV; <cmd>'`) vs Option 2 (`env -u BASH_ENV bash --noprofile --norc -c '. /etc/profile.d/CP.sh; unset BASH_ENV; <cmd>'`):**
   - **(i) MDS export now:** **Option 1 is safer right now.** `mds_backup` is a `csh` script that depends on `MDSprofile.sh`, `$CPMDIR`, and standard login `PATH`/ulimits from `/etc/profile`. Option 2 skips `/etc/profile` and assumes `/etc/profile.d/CP.sh` completely sets the MDS environment without vendor proof ([`MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md` §A.1](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md#L44-L53)).
   - **(ii) 77 gateway reads:** **Option 1 is much safer.** 58 of the 77 gateway reads in [Appendix 1](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md#L196-L276) rely on `vsenv`, which is a shell function loaded by the Expert login profile ([`InventoryCapabilityExecutor.java`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/ui2/worker/src/main/java/com/securityexpert/nexus/ui2/worker/inventory/InventoryCapabilityExecutor.java#L1813-L1814)), plus `/sbin`/`/usr/sbin` in `PATH` (`ip`, `arp`, `ethtool`, `clish`). Option 2 (`--noprofile --norc`) has not been tested across Gaia gateway versions and risks breaking `vsenv` or `PATH`.
   - **(iii) Two Class-2 failover commands (`cp_failover_down_vsid`, `cp_failover_up_vsid`):** **Option 1 is safer.** Altering shell startup to `--noprofile --norc` on a live cluster failover command (`vsenv <VSID> && clusterXL_admin down/up`) introduces unnecessary operational risk.

2. **Bash, `csh`, formatting, and quoting pitfalls in the literals as written:**
   - **Format specifiers (`%1$s`) and `$$` / `$?` in `L1b`:** Safe. [`MdsExportPlan.with()`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/ui2/worker/src/main/java/com/securityexpert/nexus/ui2/worker/backup/cp/MdsExportPlan.java#L51-L53) calls `String.format(template, workDir)`. In `java.util.Formatter`, `$` has no special meaning outside a `%` conversion token, so `echo $$`, `$CPMDIR`, and `$?` pass through untouched while `%1$s` substitutes `workDir` across all four positions ([`MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md` §A.2](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md#L64)).
   - **`setsid nohup` and `$$` as session ID (`L1b`):** Works because of the trailing `; echo $? > %1$s/mds_backup.rc`. Because the pipeline ends with `&`, the SSH exec shell runs `setsid nohup bash -lc '...'` in a background subshell (`PID != PGID`), so `setsid(2)` creates a new session in place and `exec`s `nohup` → `bash -lc`. That `bash -lc` process is the session leader (`SID == PID == $$`), and because there is a trailing command (`; echo $? ...`), `bash` does not `exec`-optimize `mds_backup` and stays alive for the lifetime of the export.
   - **Phase 2 vs Phase 3 contradiction in [`CpFailoverJobExecutor.java`](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/ui2/worker/src/main/java/com/securityexpert/nexus/ui2/worker/failover/CpFailoverJobExecutor.java#L456-L600) ([`FIX_CONTRACT` §A.3 vs §A.4](file:///Users/OzanDur/Codo/nexus-mdsstorm-1111/docs/design/MDS_FORK_STORM_FIX_CONTRACT_2026_11_11.md#L88-L103)):**
